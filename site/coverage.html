Power Platform local development: what runs on your machine, and what does not

Paqvilo reads the Power Pages and Solution sources you export with the Power Platform CLI and runs a working model of them on localhost. This page lists each development scenario, how it is executed, and where the model stops. For the commands, see the developer guide.

  • Runs locallyYour own code executes on your machine.
  • SimulatedPaqvilo's model of the platform answers, from your exported metadata and local data.
  • Live environmentThe real platform answers. Actions can change real data.
  • Static analysisSources are read. Nothing is built or executed.
  • LimitedWorks within the stated bounds, or only after you opt in.

Power Pages local development

Two tools read the same pac pages download export. Neither uploads or deploys.

Run the site on localhost (Mirage) Simulated

You can

  • Render pages from Liquid web templates, content snippets, page copy and language variants.
  • Use basic forms, multistep forms and lists built from the exported metadata.
  • Sign in as local personas with web roles and see table permissions (global, contact, account, parent and self scopes) applied.
  • Call the Power Pages Web API at /_api/ with its site-setting and token rules.
  • Save a source file and have the open pages reload.

Boundaries

  • A model of the documented contracts, not the hosted service. An unsupported tag or control is reported as a diagnostic instead of being guessed.
  • A multistep form that starts on a Condition step is reported as unsupported; modern lists lack some actions.
  • Standard, enhanced and code-site (SPA) exports differ in what the sources reveal. Missing managed metadata can leave a binding unresolved.

Preview local edits on the deployed portal (Lense) Live environment

You can

  • Serve local JavaScript, CSS, images and fonts in place of the deployed web files.
  • Override the JavaScript and CSS blocks of pages, basic forms, multistep form steps and lists, and patch literal markup in web templates, snippets and page copy.
  • See a saved stylesheet swap in place, and switch one key between Local and Online.
  • Pick an element and open the source file that produces it.

Boundaries

  • Liquid, Dataverse, authentication and server logic run online. An edit that needs them is listed as needing deployment.
  • It is the real site: submitting a form or calling the Web API changes real data.
  • Only your dedicated browser sees the overlay. Nothing is written to the environment.

Local Dataverse Web API and SDK endpoint

A local organization for integration code and API tests, without a development environment.

Simulated

You can

  • Call OData at /api/data/v9.x/: create, read, update, delete and upsert, $metadata, $batch with change-set rollback, FetchXML, saved queries, alternate keys, change tracking and file columns.
  • Connect ServiceClient and CrmServiceClient through the SOAP Organization service, and read with SQL over a read-only TDS endpoint.
  • Sign in with MSAL against a local token authority: client credentials, authorization code with PKCE, device code and on-behalf-of.
  • Test security roles, teams, sharing, impersonation and column security.

Boundaries

  • Off by default beside a portal: enable mirage.dataverse. A dataverse-api runtime has it on.
  • The .NET SDK clients need the endpoint on port 80; MSAL clients need TLS and the local CA file.
  • Search is a simple token matcher, TDS refuses CTEs, window functions and writes, and metadata writes need the deep simulation level.
  • Not a hosted service: no external federation, and tokens are local to the runtime.

Dataverse plug-in testing and debugging

Run the plug-in steps of your Solution on local writes, and debug the original C# in VS Code.

Simulated pipelineRuns locallyWindows for C#

You can

  • Run registered steps in pre-validation, pre-operation and post-operation, with images, shared variables and asynchronous jobs.
  • Choose per step: the original .NET Framework assembly, a JavaScript handler, a JSON mock, a placeholder or disabled.
  • Set a breakpoint in your C# source and attach VS Code to the plug-in host, from a Debug DLL and PDB. No Plug-in Profiler and no environment.
  • Evaluate low-code plug-ins (Power Fx) and read plug-in trace logs and the request trace.

Boundaries

  • Original assemblies load with the Dataverse SDK assemblies: on Windows x64 with the .NET Framework compiler, on macOS and Linux with the .NET 10 SDK or later. Without either, use handlers or mocks.
  • The plug-in host is not a sandbox: your assembly runs with your own user's rights.
  • An SDK call the local pipeline does not model throws LocalPluginSdkUnsupported. Steps of equal rank run in step-id order.
  • No hot reload: rebuild, then restart the runtime.

Model-driven apps on localhost

Open the apps of an exported Solution and test form scripts and commands against local rows.

SimulatedScripts opt-in

You can

  • Open an app at /main.aspx: sitemap, views with search, sort, paging and filters, main forms, lookups, subgrids and web resources.
  • With modelDriven.trustedExtensions, run form event handlers, classic and modern commands and PCF controls.
  • Rely on a bounded Xrm and formContext client API that throws on a member it does not implement, instead of silently doing nothing.

Boundaries

  • No charts, business process flows, Advanced Find, quick create forms, global search or Power BI. Dashboards show their lists only.
  • File and image controls are read-only.
  • Scripts run only after you opt in, because they are your code running in your browser.

Canvas apps in a local player

Play a canvas app from its source and see which formula produced what.

Simulated

You can

  • Run an app from an .msapp file or extracted Src/*.pa.yaml sources at /_apps/canvas/<app>.
  • Have its Power Fx evaluated by a local interpreter on local Dataverse tables.
  • Inspect a control's source file and line, the app state and formula errors.
  • Edit a source folder and reload, or drive the app over HTTP from a test.

Boundaries

  • Behaviour, not pixel fidelity: no device controls and no Studio round trip.
  • Delegation is approximate: a non-delegable query reads 500 rows and says so.
  • A connector works only with a local implementation you provide.
  • The player needs a local Dataverse user; a visitor without one gets 401.

Power Apps code apps with Vite and HMR

Develop a code app against local Dataverse data instead of a tenant.

Runs locallySimulated host

You can

  • Let mirage dev start each app's dev server and open it at /_apps/code/<name>/.
  • Keep the Power Apps SDK imports of your app working through a Vite plug-in, with hot module replacement and source breakpoints.
  • Switch apps, set parameters and watch connections and requests in a workbench.

Boundaries

  • A stand-in for the host contract, not the Power Apps player or its Local Play.
  • A connector call answers 501 unless you supply a local simulation. Dataverse calls use local data.
  • The bridge follows the SDK's internals: pin the SDK version and retest when you upgrade it.

PCF code components on real forms and local data

Host your built control where it will live, bound to rows instead of test-harness inputs.

Runs locallySimulated host

You can

  • Mount standard field controls on portal pages ({% codecomponent %}) and portal form fields.
  • Mount field controls, dataset controls on subgrids and virtual (React) controls on model-driven forms.
  • Mount scalar controls in the canvas player (canvas.codeComponents: true).
  • Have context.webAPI read and write local records on portal pages and forms.

Boundaries

  • Production bundles from your Solution; Paqvilo does not build the control.
  • Portal pages host no virtual controls and no PCF in native lists or subgrids.
  • Model-driven dataset controls take one sort column and one AND filter group.
  • Virtual controls need the platform libraries supplied by your project.

Power Automate cloud flows and server logic

Exercise what a page or a row change triggers, without calling a cloud connector.

Simulated flowsServer logic runs locally

You can

  • Run exported cloud flows in a local interpreter: Power Pages, manual, HTTP, recurrence and Dataverse row triggers; conditions, loops, variables, expressions, child flows and approvals.
  • Have Dataverse connector actions read and write local rows.
  • Execute Power Pages server logic JavaScript as exported.
  • Replace any operation with a JSON mock or a provider from your project.

Boundaries

  • No cloud connector is ever called. Other connectors use loopback URLs, fixtures or your providers.
  • A closed set of expression functions; action retry policies and static results are not modelled.
  • Classic (XAML) workflows are not interpreted.

Request tracing and the Monitor

See why a local request rendered, saved, was denied or failed.

Runs locally

You can

  • Read each request as one tree: page render with its templates, Web API or form step, Dataverse operation, plug-in stages, flows and connector calls.
  • See the table-permission decision that hid a row or refused a write.
  • Use the Monitor in /_sim/, paqvilo mirage trace or the test API, and export JSON, NDJSON or OTLP.

Boundaries

  • Local runtime only. Lense does not trace the live platform.
  • On by default at summary; full adds redacted payloads. Kept in memory unless you set persist.

Offline analysis of Power Platform sources

Review an export before you commit or deploy it.

Static analysis

You can

  • Run paqvilo analyze on a folder or a project: rules for Dataverse and ALM, model-driven apps, canvas apps, PCF, code apps, cloud flows, connectors and Power Pages.
  • Get each finding with its rule, file and line, as text or --json.
  • Set the failing severity with --fail-on for a CI gate.

Boundaries

  • Reads sources only: nothing is built or executed and no tenant is contacted.
  • It complements the solution checker of your environment; it does not replace it.

Guide: analyze sources →Rules reference ↗

Automated tests, CI and AI coding agents

Check a change without an environment, a tenant or a person clicking.

Runs locally

You can

  • Write Node tests against a running local runtime: sessions as personas, Web API calls, records and traces, and, with an in-process simulator, a fixed clock and sequential ids for repeatable runs.
  • Parse --json output from the status, inspection, trace and analysis commands.
  • Give a coding agent a bounded browser API: sessions, pages, events, snapshots, screenshots and navigation, confined to one origin.

Boundaries

  • A passing local test is evidence about the local model, not proof of platform behaviour.
  • Browser tests need Edge or Chrome on the machine or runner.
  • Neither tool grants an agent permission to change live data or deploy.

BEFORE YOU RELY ON IT

Limits that apply to every scenario

  • A simulation, not an emulator. Mirage models the parts of Power Pages and Dataverse it documents and reports what a source uses beyond them. Check what matters in a real environment before you release.
  • No cloud connectors. Flows, canvas apps and code apps never reach a real connector locally. Dataverse actions use local data; for the rest you supply a provider or a mock.
  • Windows, macOS and Linux; C# debugging on Windows. The toolkit needs Node.js 26.13.1 or later in the 26.x line and Edge or Chrome. Original .NET Framework plug-in assemblies load on Windows x64, or on macOS and Linux with the .NET 10 SDK or later.
  • Deployment and licensing are unchanged. Mirage and Lense do not deploy or host production sites, and nothing here replaces Microsoft licences. An environment is written to only when you ask: by the paqvilo dataverse commands that apply, register or publish, by Mirage started with --allow-live-writes, and by what you do yourself in a Lense browser.
