# Server logic and cloud flows

Mirage inventories exported operations automatically. Open `/_sim/#operations` to review their source, route, access and local behavior. The catalogue includes portal server logic and cloud-flow consumers, matching enhanced site records in selected Solutions, and Solution workflow definitions.

An unlinked workflow remains visible and permits local mock/disabled configuration without an invented portal route or role grant. Configuration alone does not invoke or activate it. A supported activated Dataverse row trigger with an explicit backend profile can run without a portal consumer; a Power Pages Request workflow needs its consumer export to establish a route and web-role binding. Its role checks still apply when the response is mocked.

Solution plugin steps also appear in Backend operations. They run through supported local CRUD stages, rather than a portal URL. Select a step to review its table, message, stage, filtering columns and source. Configure a target-field mock, validation rejection or trusted project handler. See [Dataverse plugins](dataverse-plugins.md) for the contract and execution limits.

## Choose local behavior

| Mode | Result |
| --- | --- |
| Placeholder | HTTP 501 identifies an operation without a supported local implementation |
| Supported exported flow | Run imported basic actions for a Power Pages Request or supported activated Dataverse row trigger |
| JSON mock | Set a response body and status for success, empty, validation or failure scenarios |
| Exported server logic | Explicitly enable exported JavaScript against the local data store |
| Project provider | Register a trusted pack handler for business logic or unsupported integrations |
| Disabled | Deliberately skip the flow or exact action and retain a trace of that choice |

Select an operation, save its local behavior and call its exported route from your portal. **Use source default** removes a local override. Overrides affect simulation state; they do not deploy the source or activate an online flow.

## Execution boundary

Imported routes retain exported web-role checks. Local data access applies the current identity and table permissions. Exported server logic can query and change local records through supported Dataverse helpers. Writes require a verified HTTP write request and native CSRF checks; Liquid helper calls remain read-only.

Exported server logic reaches the host through one channel. `Server.Connector.Dataverse.InvokeCustomApi(httpMethod, url, payload)` runs the custom API through the organization's operation registry (unbound `name`, or `set(id)/Microsoft.Dynamics.CRM.name`; function parameters as inline literals) as the site's application user, never SYSTEM (see [server logic site settings and principal](#server-logic-site-settings-and-principal)); a bound row must be readable by the signed-in contact under its table permissions, else the call answers 403. It answers the server-object envelope (`StatusCode`, `Body`, `IsSuccessStatusCode`, `ReasonPhrase`, `ServerError`, `ServerErrorMessage`, `Headers`). `Server.Connector.CloudFlow.TriggerAsync(flowId, payload)` runs the site's cloud flow through the same pipeline as `/_api/cloudflow/v1.0/trigger/<guid>`, with its web-role check; the payload carries `siteId` and `userId`, and a flow without a Response action answers 202 with an empty `Body`, reported as success. `Server.Connector.HttpClient.GetAsync/PostAsync/PutAsync/PatchAsync/DeleteAsync` is a contract: a URL is first rewritten by the connections' `settings.rewrites`, and only a loopback target is called (redirects refused); any other host answers `StatusCode` 502, `ServerError: true`, `ServerErrorMessage: 'HTTP target is not a declared local service'` and records `SERVER_LOGIC_HTTP_REFUSED`. `Server.Logger.Log/Warn/Error` lines go to the diagnostics stream (`SERVER_LOGIC_LOG`) with the operation id (`Server.Context.ActivityId`). Exported server logic also receives `environmentVariables`. A bridge whose host service is absent answers the envelope with status 501 and `ServerError: true`, never a success.

### Server logic site settings and principal

The `ServerLogic/*` site settings apply. `ServerLogic/Enabled` false refuses every server-logic call with 403 `ServerLogicDisabled` and records `SERVER_LOGIC_DISABLED`. `ServerLogic/AllowedDomains` (comma or semicolon separated; a domain also allows its subdomains) and `ServerLogic/AllowNetworkingToAllDomains` (false with no list refuses every host) are checked against the original HttpClient host before any local rewrite: a refused host answers the 403 envelope and records `SERVER_LOGIC_HTTP_DOMAIN_BLOCKED`. `ServerLogic/TimeoutInSeconds` (default 120, at most 240) is read, but a local run is always bounded at 5 seconds; a configured value above that records `SERVER_LOGIC_TIMEOUT_LOCAL` (info).

`Server.Connector.Dataverse.InvokeCustomApi` never runs as SYSTEM. It runs as the site's application user: the observed one (`observed.portalApplicationUserId`) when the organization has that row, else a local application user named `# Portals-<site name>`, created once (System Administrator stands in for the native Portal Application User, Service Writer and Service Deleter roles). A bound row must be readable by the signed-in contact under its table permissions; otherwise the call answers 403. The capability record `serverLogic` lists the bridge levels: Dataverse, InvokeCustomApi, CloudFlow, Logger, EnvironmentVariable and site settings at behaviour, HttpClient at contract (`SERVER_LOGIC_HTTP_REFUSED`).

### Flow interpreter

Imported flow definitions run through a bounded local interpreter. Supported actions include variables, Compose, conditions, scopes, foreach (sequential by default; a top-level `Foreach` with `runtimeConfiguration.concurrency.repetitions` from 1 to 50 runs that many iterations at once, and iterations that run concurrently and write a variable need an explicit mock), Until, Switch, runAfter, Response/Terminate, Wait, the data operations ParseJson, Select, Query (Filter array), Join and Table (CSV or HTML), child flows (`Workflow`), the `Http` action and the Dataverse connector operations listed under [connections and connectors](#connections-and-connectors). ParseJson validates its content against its schema and fails `ValidationFailed` on a mismatch. `Until` runs its actions, then evaluates its expression, at most `limit.count` times (default 60, at most 5000; a count above the local iteration limit is refused); reaching the count ends it Succeeded and reaching `limit.timeout` (default PT1H) ends it TimedOut; a Wait inside it cannot suspend. A pack `flowActions` export adds an action type (see [data packs](data-packs.md)); such an action runs with resolved inputs, is journalled like a connector action and is contract only. Concurrent branches (actions with no runAfter path between them) start together: every action whose runAfter dependencies have all settled starts, a provider call that answers asynchronously leaves its sibling branches running, and a join waits for every dependency. A waiting action (a `Wait`, a waiting approval or a waiting child flow) holds only its own branch: the built-in actions of the other branches keep running and the run suspends when no branch can progress, so a Response in a branch concurrent with a Wait answers before the run waits. Once a branch waits, provider-backed actions (connector, `Http`, child flow, pack actions, changesets) and further waits of the other branches run after the resume. `Terminate` stops the run at once: no action starts after it. A `Terminate` with `runStatus` `Failed` or `Cancelled` fails the run with its `runError.message` (code `LocalFlowTerminated`). Two branches that cannot both run (runAfter statuses of the same predecessor that exclude each other, such as a success path and a failure handler) are not concurrent. Two concurrent branches that write the same variable, where one writes a variable the other reads (`variables('<name>')` in its inputs, expression or foreach), or that both answer a Response, still need an explicit mock or disabled choice, because their result depends on the interleaving. Unsupported expressions, connectors and execution settings require an exact per-action mock or disabled choice. The admin contract lists source action paths and records per-action mode/status/errors. Response headers are validated locally; unchosen branches retain Skipped states. A connector action accepts `runtimeConfiguration.secureData` and `inputs.retryPolicy` (see [flow runs, waits and approvals](#flow-runs-waits-and-approvals)); an action-level `retryPolicy`, `operationOptions`, `limit` (except on `Until`) or `staticResults` setting and arbitrary external connectors are not silently approximated.

WDL string interpolation preserves literal `@@{...}` escapes and exact numeric digits, including numbers within interpolated collections ([Microsoft expression syntax](https://learn.microsoft.com/en-us/azure/logic-apps/workflow-definition-language-schema#expressions)). Variable declarations require the global workflow level; nested declarations are rejected before execution unless the action or its containing branch has an explicit mock/disabled choice ([Power Automate variables](https://learn.microsoft.com/en-us/power-automate/create-variable-store-values)).

Flow completion follows terminal branch statuses: a successful failure handler resolves its branch, while a skipped terminal action inherits its predecessor's completion status. Historical action statuses remain available for inspection ([Microsoft error handling](https://learn.microsoft.com/en-us/azure/logic-apps/error-exception-handling)). Response accepts 2xx, 4xx and 5xx status codes; a static 3xx status is rejected before execution and a computed 3xx status fails when the action runs ([Response schema](https://learn.microsoft.com/en-us/azure/logic-apps/logic-apps-workflow-actions-triggers#response-action)).

Triggers run locally as follows. A Power Pages Request trigger runs from its portal consumer and a manual (`Button`) trigger runs as a child flow or on demand. An HTTP Request trigger (`kind: Http`) runs on demand through `POST /_sim/api/flow-triggers/<flowId>`; its signed callback URL is not served. A `Recurrence` trigger (`frequency` Second to Month, `interval`, optional `startTime`, `timeZone` and `schedule`) runs on the runtime scheduler once its flow has the exported choice and explicit local activation. `timeZone` is an IANA time-zone name resolved through the platform's Intl database; a `startTime` without `Z` or an offset is wall-clock time in that zone, and with `Z` the zone is ignored. A Windows time-zone id such as `W. Europe Standard Time` maps to its IANA zone through the Unicode CLDR 45 windowsZones table (territory 001, `mirage/lib/windows-time-zones.mjs`); an id that is neither in that table nor known to Intl is refused by name (`Coordinated Universal Time` is read as UTC). `schedule` takes `hours` and `minutes` (Day, Week and Month), `weekDays` (Week) and `monthDays` (Month, `-1` for the last day); a schedule on another frequency, or an unknown schedule key, is an explicit error. With a schedule, or with a non-UTC zone on Day, Week or Month, occurrences are wall-clock times in the zone (across daylight-saving changes), no sooner than `startTime`; unset hours, minutes, week day and month day come from `startTime` (or the moment the host was armed). Without them, occurrences follow `startTime` (or the arming moment) in whole intervals. Missed occurrences are not back-filled. A connector webhook or polling trigger runs only when a pack `flowTriggers` export hosts its connector operation (contract): the host subscribes it on activation, it starts a tracked run for every `fire(body)`, a polling trigger's `poll()` runs at its recurrence `frequency` and `interval` from its `startTime` (never before it; a schedule on a polling connector trigger does not apply, as for managed polling triggers), and it is unsubscribed when the flow is no longer enabled or the runtime closes. The Dataverse "When an action is performed" trigger (`BusinessEventsTrigger`, parameters `catalog`, `category`, `entityname`, `sdkmessagename`; `entityname` `none` for an unbound action) is hosted once its flow has the exported choice and explicit local activation: each committed run of the named custom API (bound to that table, or unbound) records a committed event that stages a durable Ready `asyncoperation` job, like a row trigger, and the job starts a tracked run (trigger type `Automated`) whose trigger body is `{ InputParameters, OutputParameters }`. An action inside a `$batch` changeset or other transaction that rolls back starts no run, and a job staged before a restart runs after it. Catalog and category are not checked against Catalog rows. Without a host, another connector trigger answers `Unsupported trigger <type>/<operation> (<connector>; no pack flowTriggers entry hosts it); configure an explicit flow mock or disable it.` Request triggers with conditions, splitting, concurrency, recurrence, operation options or unsupported inputs remain explicit capability errors.

Both hosts re-synchronise the Recurrence and connector trigger hosts when the runtime starts and after an operation override is applied, so enabling `{ mode: 'exported', activation: 'local-enabled' }` through `/_sim/api/operations/<key>` or `PATCH /_sim/api/config` schedules the flow immediately. The `flow-triggers` capability record is part of the host registry. Solution custom connectors (`Connectors/*_openapidefinition.json`) are registered as `custom-connector:<name>` providers and follow a source reload.

A variable declared without an initial value gets no inferred default.

GetItem supports comma-separated direct-column `$select` through the existing local SDK ColumnSet. Ordinary reads retain their current behavior; selected reads retain the primary key and attributes added by Retrieve plugins. `$expand`, lookup aliases and other connector options are rejected as unsupported ([Get a row options](https://learn.microsoft.com/en-us/power-automate/dataverse/get-row-id#advanced-options)). Connector HTTP headers, full metadata and precise native response envelopes are not reproduced.

Each Dataverse connector request uses an explicitly registered project `flowIdentities` backend profile or, without one, the principal of its bound connection (see [connections and connectors](#connections-and-connectors)). Portal role access and flow connection identity are separate. A later failed flow action preserves earlier completed connector writes. Each individual connector operation retains its own plugin transaction boundary. A row-triggered run can succeed without an HTTP Response; a request-triggered run cannot invent one.

Activated imported Dataverse triggers support added/modified/deleted and combined callback-registration messages, explicit Organization scope, scalar submitted-column selection and saved-row OData filters. An unchanged submitted update column still matches selection. Create/Delete ignore update select columns; lookup-column selection requires metadata and is ignored. Other ownership scopes, runAs, Delete-filter payload semantics, trigger conditions and unsupported source settings are reported as unsupported. Draft or unknown activation stays inactive by default. **Explicitly activate this source locally** enables a local test choice and records the override without altering the export or online flow.

Post-save queues preserve only actually committed events. Failed primary writes emit no trigger, while independently committed top-level PreValidation SDK writes retain their events. Recursive plugin/flow chains have bounds and drain together before reload/stop. The trigger queue never drops committed runs: past 100 queued runs (and each further 100) it records `FLOW_TRIGGER_BACKLOG` and still runs every one in order. Each accepted run is a Ready asyncoperation row (System Event) holding the committed event in its `data` column, run FIFO by the store's one durable job runner together with asynchronous plug-in steps (see [Dataverse plug-ins](dataverse-plugins.md)); the row is removed when the run ends and the run is reported by `FLOW_TRIGGER_*` diagnostics. Ready runs saved in the state file resume once after a restart. Tests drive them with a manual scheduler (`createScheduler({ clock: fixedClock(), manual: true })` passed as the organization runtime's `scheduler`) and `runDue()`. Job errors are separate from the original committed response. This local queue is not the native Power Automate scheduler or its retry service.

## Connections and connectors

Connector actions run through one connector runtime (`mirage/lib/connector-runtime.mjs`). Each `OpenApiConnection` action, the built-in `Http` action and a Dataverse trigger resolve along this chain; every failed hop is a coded error, never an implicit success:

1. the action `host.connectionName` names an entry of the flow's `properties.connectionReferences`, which gives the connection reference logical name;
2. the `connectionreference` row with that logical name gives the bound `connectionid`;
3. the project `connections[<connectionid>]` entry gives the connector, provider, principal and settings;
4. the provider runs the operation.

An action without a connection reference (the built-in `Http` action) uses `connections.<connectorId>` (for example `connections.http`) when declared, otherwise the connector's built-in provider. A pack `flowIdentities[<processId>]` profile is a per-flow override: it takes precedence over a connection principal and binds Dataverse actions on its own.

| Provider | Level | Behaviour |
|---|---|---|

A custom API handler called from a flow run joins the run's transaction. Without the organization (a bare connector runtime) these four answer `OperationUnsupported` (501). List rows answers at most 5,000 rows per page ([Use lists of rows in flows](https://learn.microsoft.com/power-automate/dataverse/list-rows#skip-token)); when more rows match, the body carries `@odata.nextLink`, and passing its skip token back as `$skiptoken` (or a `paginationPolicy`) reads the next page. Connection entries never hold credentials: a credential-looking key (secret, password, key, token) must reference `env:NAME` or `variable:NAME`, and rewrite prefixes cannot carry user information, a query or a fragment. A custom connector connection takes `settings.auth` (`apiKey`, `username` and `password`, a static OAuth `token`, or `clientId` and `clientSecret`; every value an `env:NAME` or `variable:NAME` reference) and `settings.parameters` (connection parameter values for policy expressions). An OAuth connector whose security definition uses the client credentials flow (`flow: application`) and has no static `token` posts `grant_type=client_credentials` with the client id, secret and the definition's scopes to the definition's `tokenUrl` (after the rewrites, loopback or a pack fixture only) and caches the token in memory until its `expires_in`; tokens and secrets never reach state, diagnostics or `/_sim` answers. A missing client reference or a refused token request answers 401 `ConnectionUnauthorized`. An authorization code connector (`flow: accessCode`) is signed in through `POST /_sim/api/connections/<connection id>/authorize` and answers 401 `ConnectionUnauthorized` until it is. Any other OAuth flow without a static `token` answers 501 `OperationUnsupported` naming the flow.

`CreateRecord`, `UpdateRecord` and `DeleteRecord` run the organization record pipeline (state defaults, record hooks, audit and version columns, alternate-key answers), and `GetItem`/`ListRecords` return the Web API read projection (computed columns, column security). An asynchronous record-hook remainder that fails after the action returned is reported as `SDK_DEFERRED_EFFECT`.

Errors use these codes: `ConnectorNotConfigured` (501), `ConnectionNotBound` (409), `ConnectionUnauthorized` (401, the named principal is not declared), `PermissionDenied` (403), `OperationUnsupported` (501), `ProviderUnavailable` (503, including a non-loopback URL), `ProviderTimeout` (504) and `ProviderFailed` (502, including a refused redirect). Dataverse backend errors such as `LocalBackendPermissionDenied` keep their existing codes. A failed call fails its action, so `runAfter` failure branches handle it. A connector, `Http`, child-flow or pack flow action answer of 400 or above, including the last answer of an exhausted retry policy, also fails the action: the action's `error` is `{ code: 'ActionFailed', message }` and its outputs keep the status code, headers and body. A provider call that throws (an unreachable provider, a refused grant, a pack error) fails the action with `error: { code: 'ActionFailed', message, cause: { code } }` and keeps `{ error: { code, message } }` as its outputs. A child flow Response of 4xx or 5xx fails its parent action the same way. Every call records `CONNECTOR_INVOKE` with connector, operation, reference, connection, provider, principal id, caller, status, duration and correlation id; parameter values, URLs, headers and bodies are never recorded.

A connector action that declares only `runtimeConfiguration.paginationPolicy.minimumItemCount` follows `nextLink` pages until it has that many items, at most 10 pages; a truncated result records `CONNECTOR_PAGINATION_TRUNCATED`. Without the policy only the first page is returned. A later page that answers a non-2xx status fails the action with that page's status and body. When every page is read the result carries no `nextLink` or `@odata.nextLink`. Dataverse `ListRecords` actions accept the same policy.

The operation contract lists `connections` (name, connector, reference, connection id, provider, bound, using actions) and each connector action's `connection` (`referenceLogicalName`, `bound`, `provider`). An unbound reference keeps its action unsupported, so the flow needs a per-action mock or disabled choice. A discovered flow defaults to exported only when its trigger is supported and every connector call, including a Dataverse trigger, resolves to a bound connection; otherwise it stays a placeholder.

### Flow runs, waits and approvals

The flow run store (`createFlowRunStore` in `mirage/lib/flow-runs.mjs`) writes one standard `flowrun` row per run with `flowrunid`, `workflowid`, `status` (`Running`, `Waiting`, `Succeeded`, `Failed`, `Cancelled`, `TimedOut`), `starttime`, `endtime`, `duration`, `triggertype`, `correlationid` and, for a failed run, `errorcode` and `errormessage`. Replay state lives in `state.simulator.flowRuns[<runId>]`: definition hash, trigger input, the configured `steps`, the journal of executed connector actions (`{ status, outputs }` per action path) and the current wait. Trigger input is dropped when the run ends. The store keeps the newest 200 runs and the journals of the newest 50 finished runs, and drops finished approvals beyond 200 (pending approvals stay); older ones are removed with a `FLOW_RUN_JOURNAL_PRUNED` diagnostic that counts `runs`, `journals` and `approvals`. Running and waiting runs are never pruned.

A waiting run records `wait = { kind: 'delay' | 'approval' | 'webhook' | 'child', id, actionPath, until?, timeoutAt?, assignedTo? }` and its row becomes `Waiting`. Wait timers run on the store's scheduler (`runDue()`/`advance(ms)` with a manual one): at `until` a delay ends `Succeeded`, at `timeoutAt` the action ends `TimedOut`, a pending approval becomes `TimedOut` and `runAfter: ['TimedOut']` branches can run on resume. The timers are in memory; `rearm()` schedules them again from the recorded waits after a restart. Without a host resume function a timeout ends the run `TimedOut`.

Resume is deterministic replay. The run's non-secret flow parameter values (environment variable values and defaults) are frozen in the run state when it starts, and a resume replays those values, so a changed environment variable never changes a waiting run; `Secret` parameters are never stored and are resolved again on resume. `resume(runId, outcome)` turns the run back to `Running` and answers `{ steps, journal, input, parameters, replay, processId, correlationId, definitionHash }`, where `replay` lists the journalled action paths and `journal` maps each to `{ status, outputs }`. Journal paths carry the occurrence: the second run of a loop body's connector action is `<path>#2`, so a run that called a connector inside a loop resumes and replays each iteration's answer. `steps` is the `executeFlowDefinition` steps map: the steps configured at start, then every journalled action path as `{ mode: 'mock', status, outputs }`, then the suspended action path as `{ mode: 'mock', status: outcome.status, outputs: outcome.outputs }`. Running the same definition and input with that map answers completed connector actions from the journal, so their writes are not repeated. A replay that reaches a live provider call (connector, `Http`, child flow or pack action) while a journalled action path is still unreplayed, or that ends with one unreplayed, took another path than the original run: it fails the run `NotResumable` with the reason `ReplayDiverged` before the provider is called. A second resume of the same wait answers `FlowRunNotWaiting` (409). Secure outputs (an action with `runtimeConfiguration.secureData` covering `outputs`, including a waiting approval or child flow action, whose wait then carries `secure: true`) are never written to state: the journal holds `{ status, secure: true }` only and the clear answer stays in process memory until the run ends. A resume in the same process replays it; a resume after a restart fails `NotResumable` (409) naming the action (`SecureOutputs (action <path>)`). An action that only takes a `Secret` parameter as input journals its outputs and resumes normally. A run whose definition hash changed fails `NotResumable` (409) instead of resuming. An on-demand run started without a Response requirement (`context.background`, as `POST /_sim/api/flow-runs`) keeps that across its resume, so a Button flow with a Wait and no Response ends `Succeeded`.

The `approvals` provider stores each approval in `state.simulator.approvals[<id>]` (`title`, `assignedTo` split on `;`, `details`, `status` `Pending` → `Approved` | `Rejected` | `TimedOut` | `Cancelled`, `responses`). `CreateAnApproval` answers the approval at once; `StartAndWaitForAnApproval` and a pending `WaitForAnApproval` answer `{ suspended: { kind: 'approval', id, timeoutAt, assignedTo } }` only to a caller that passes `context.canSuspend`, and `FlowSuspendNotWired` (501) to any other caller. The default `timeoutAt` is 30 days, the Power Automate run duration limit. A response (`Approve` or `Reject`, case-sensitive) completes the approval and answers the action outputs `{ statusCode: 200, body: { name, title, details, outcome, requestDate, completionDate, responses: [{ responder, requestDate, responseDate, approverResponse, comments }] } }`, field names from the documented Approvals output definition. Status codes and the dynamic output envelope are not reproduced exactly.

Both hosts attach one run store to the organization (`createHostFlowRuns`, composed in `mirage/lib/organization-host.mjs`): `attach(api)` sets `api.flowRuns` and `api.resumeRun` and re-arms recorded wait timers, the host's capability registry lists the store as `flow-runs`, and the host closes it after the committed-work backend and before the organization. With it, `runTrackedFlow` (`mirage/lib/flow-runtime.mjs`) runs every flow kind as a tracked run: activated row triggers, `ExecuteWorkflow` (`runCloudFlow`), portal request flows (`runExportedCloudFlow`) and child flows. It starts or resumes the run, executes the definition inside the caller's transaction, journals the executed connector actions, then suspends the run or completes it `Succeeded`/`Failed`. Run store writes happen outside that transaction, so a rolled-back execution keeps its `Failed` row. Resume replays the current exported definition, identity and connections of the flow; a flow whose definition left the sources fails `NotResumable`.

A run suspends on a `Wait` action (`inputs.interval { count, unit }` with unit `Second` to `Week`, or `inputs.until.timestamp`) or on a waiting Approvals action. Suspension is only possible outside loops; inside a `Foreach`, and in a runtime without a run store, a waiting action answers `FlowSuspendNotWired` (501), so mock or disable it there. A portal request flow that waits before its Response answers 202 `{ runId, status: 'Waiting' }`.

`inputs.retryPolicy` on a connector action takes `{ type: 'fixed' | 'exponential' | 'none', count: 1–4, interval: <ISO 8601 duration, at most one day> }`. `ProviderUnavailable`, `ProviderTimeout`, HTTP 429 and 5xx answers are retried on the runtime scheduler (exponential waits interval × 2^(n−1)), and each attempt is journalled under `attempts`. A retry policy on a built-in action or with invalid values fails validation as `InvalidRequest` (400).

A `Workflow` action runs its child flow through the internal `flow` connector (`RunChildFlow`) as its own run with trigger type `ChildFlow`, inside the parent's transaction. Child flows nest at most 16 levels deep (`FLOW_MAX_DEPTH`, `ChildFlowDepthExceeded`, 400); the same constant caps the row-trigger chain depth limit (default 8). The child needs an exported definition (`ChildFlowNotFound`, 404) with a manual (`Button`) Request trigger (`ChildFlowTriggerUnsupported`, 400) and a Response for its parent. A child in mock, disabled or handler mode fails `ChildFlowNotExecutable` (501); a child that answered its Response before it waits answers the parent at once and keeps running. A child that waits before answering suspends its parent on a wait of kind `child` (`wait.id` is the child run id); the child run records its owner (`parent: { runId, actionPath }`) and is never cancelled for it, and when the child completes a parent still waiting on it resumes with the child's Response (a cancelled parent is left alone) as the action outputs (a status of 400 or above, or a failed, cancelled or timed-out child, fails the action). `POST /_sim/api/flow-waits/<id>` refuses a child wait with 409 `FlowWaitOwnedByChild`. A parent action inside a `Foreach` or `Until` suspends on its iteration's journal key like any waiting action; only a parent action without a run id to suspend on (an untracked run) cancels a waiting child and fails `ChildFlowSuspendUnsupported` (501). Pack connector ids cannot be `flow`.

`CancelAllCloudFlowRuns` cancels the workflow's `Running` and `Waiting` runs through the run store, which stops their timers and cancels pending approvals, then sets any other open `flowrun` row of the workflow to `Cancelled`, in one transaction.

#### Administration routes

The flow administration routes (`mirage/lib/sim-flow-routes.mjs`):

| Route | Result |
|---|---|
| `GET /_sim/api/flow-runs?processId=&status=` | Run summaries, newest first. |
| `GET /_sim/api/flow-runs/<runId>` | One run with its journal; trigger input and secure outputs are never included, and credential-named values are redacted. |
| `GET /_sim/api/flow-waits?state=overdue\|pending` | Waiting runs and their waits. |
| `POST /_sim/api/flow-waits/<waitId>` | `{ outcome, responder, comments }` for an approval (or `{ outputs }` for a delay or webhook wait); needs `x-sim-csrf`. Records the response and schedules the host's resume of the run (202). A runtime without a resume function answers `FlowResumeNotWired` (501) and changes nothing. |
| `POST /_sim/api/flow-runs` | `{ processId, input }`: starts a tracked run (trigger type `Manual`) of a manual, HTTP Request, Recurrence or pack connector-trigger flow whose choice is its exported definition; needs `x-sim-csrf`. Answers 201 with the run summary and the flow's Response, if any; another choice answers `FlowNotExecutable` (409) and another trigger `FlowTriggerUnsupported` (400). |
| `POST /_sim/api/flow-triggers/<flowId>` | Runs an HTTP Request trigger flow with the JSON body as its trigger body; needs `x-sim-csrf`. Answers the flow's Response status and body with only its `content-type` and `x-*` headers (never `x-sim*`, cookies, `location` or CSP headers), or 202 `{ runId, status }` when it has none or waits. |
| `GET /_sim/api/flow-triggers` | The trigger hosts: one entry per Recurrence, HTTP Request and connector-trigger flow with `kind`, `state` (`scheduled`, `subscribed`, `on-demand` or `inactive`), `nextRun` and the reason an entry is inactive. Reading it only lists; the hosts follow the choices at startup and when operation choices change. |

## Local services

Azure Functions, Azurite, the Service Bus emulator and other loopback HTTP services are declared and probed, never
started, by Paqvilo. Run Functions with Core Tools (`func start`), Azurite with `npx azurite --location .paqvilo/azurite`
and the Service Bus emulator with its Docker containers, outside Paqvilo. Core talks to both emulators as providers:
`providers.storage` `kind: azurite` over the Blob REST API ([storage providers](storage-providers.md#azurite)) and
`providers.messaging` `kind: servicebus-emulator` over AMQP 1.0 ([messaging](messaging-and-outbox.md#service-bus-emulator)).

```yaml
localServices:
  functions:  { kind: http, baseUrl: "http://localhost:7071", probe: "/admin/host/status", required: false }
  azurite:    { kind: azure-storage, blob: "http://127.0.0.1:10000/devstoreaccount1", probe: "/devstoreaccount1?comp=list" }
  servicebus: { kind: service-bus, connectionStringVariable: FX_SB_EMULATOR }
  fx-api:     { kind: http, baseUrl: "http://127.0.0.1:5000" }
```

`localServiceSettings` (`mirage/lib/local-services.mjs`) checks the config: every `baseUrl`, `blob` and probe must
stay on localhost, 127.0.0.0/8 or ::1, a probe is a path on that origin, and a `connectionString` key is refused (name
an environment variable instead). `preflightLocalServices` sends one GET per service with a 2 second timeout and no
redirects, and answers `{ id, kind, reachable, status, required, message }` without throwing; messages show origin and
path only, never a query or a connection string. A Service Bus entry reads the variable at probe time and checks the
emulator's loopback health endpoint (`serviceBusEmulatorPreflight`); an unset variable is reported by name.
`describeLocalServices` lists each service as a `contract` capability with `requires: ['external-process:<id>']` and
lifecycle `external-process`.

Workers and interpreter budgets bound execution time; they do not provide an arbitrary untrusted-code sandbox. Enable exported code only from sources you trust.

External connectors, custom APIs, complex flow actions and unsupported expressions require explicit handlers, mocks or disabled choices. Mirage never forwards imported definitions to remote Power Automate. To compare a flow with the platform, compare run and action traces and resulting data from an authorized environment that runs the same exported definition.
