# Dataverse plugin registrations

Mirage discovers plugin assemblies, types and steps from selected Solution sources. **Backend operations** shows their table, SDK message, stage, execution order, mode and filtering attributes. **Inspect** links applicable steps to exported metadata and explicitly mapped C# sources. Lense uses the same inventory; exported registrations do not prove which steps are active online.

Choose a local execution mode for each discovered enabled step. Original CLR execution loads the original `IPlugin` assembly in an owned Windows .NET Framework process. It requires an explicitly trusted project descriptor, an externally installed Microsoft Xrm SDK assembly and a separate backend identity/security profile. Export discovery alone never enables a DLL. Missing CLR prerequisites do not prevent using mocks or disabled choices.

| Mode | Local behavior |
| --- | --- |
| Placeholder | CRUD continues; `PLUGIN_STEP_PLACEHOLDER` reports skipped business logic |
| JSON mock | Return a target patch or reject the write |
| Project handler | Run a trusted, explicitly registered synchronous JavaScript model |
| Original CLR | Execute the exact registered original type with the supported local SDK adapter |
| Disabled | Skip this step deliberately and record the choice |

Source mode 1 stage 40 Create/Update/Delete steps use a bounded post-save queue. Their failure is recorded separately and cannot reject the committed caller. Unsupported source contracts remain visible; explicit mock/disabled choices are still selectable. Original execution of an unsupported contract fails diagnostically. Select **Use source default** to remove a local override.

Mocks can replace a supported read query/result or bulk Targets through Backend operations, using the same typed local contracts as project handlers. The admin endpoint checks result shape, source table and execution stage before saving. An eligible explicit mock still applies its configured result when the original registration needs an unavailable image or identity adapter; diagnostics state that original logic was not executed. Unknown messages/stages do not gain an execution pipeline through a mock choice.

## What is simulated

Native Dataverse loads the registered .NET assembly into the sandbox worker and runs `IPlugin.Execute(IServiceProvider)` for every enabled step whose message, table, stage and filtering attributes match.

Mirage stores the registration rows (plug-in assemblies, types, steps and images, with the sdkmessage and sdkmessagefilter rows they reference) under Dataverse's documented validation. A step joins the live pipeline only with a trusted local implementation: a pack handler keyed by step id (`pluginSteps`) or by plug-in type name (`pluginTypes`, see `docs/project-extensions.md`), an explicitly trusted original-CLR descriptor (`pluginRuntimes`), or a `/_sim/` mock. A step without one is stored, listed and enabled like a native row, but runs as a placeholder: it is skipped and a `PLUGIN_STEP_PLACEHOLDER` diagnostic is recorded. Uploaded assembly content is inspected as bounded PE/CLI data to derive its identity and declared types. Uploading bytes never enables code execution.

`GetPluginCertificateInfo` inspects embedded PE Authenticode or NuGet `.signature.p7s` certificate metadata. The CMS signer's issuer and serial identify its certificate even when another chain certificate appears first. Inspection reports the X.509 names, SHA-1 fingerprint, self-signature result and certificate/name DER; it does not validate image signatures, establish trust, execute code or contact certificate authorities. Native DN formatting and the exact `CertificateSegment`/`CertificateSegmentV2` representation remain unverified. Unsigned content has empty certificate facts; malformed or oversized certificate structures fail explicitly.

`OnExternalCreated`, `OnExternalUpdated` and `OnExternalDeleted` expose registration filters only for virtual mappings. Their steps must use asynchronous PostOperation (mode 1, stage 40); other registrations fail with `0x80090303`. Notifications publish the supplied snapshot and schedule the local asynchronous pipeline without modifying provider-owned rows.

While the Dataverse API is on, its registration rows decide which steps run. With no registration writes the list equals the Solution's own list. A disabled step stops running, a deleted step is removed, and a step registered through the API takes the same pipeline position as a Solution step (stage, then rank).

Steps on a web hook (service endpoint) are delivered as described in [Webhooks](#webhooks). Asynchronous steps run after commit as durable jobs. Each accepted run is written as a Ready asyncoperation system job (System Event, operationtype 1; Ready 0/0) inside the transaction that commits the triggering write, so the commit carries its jobs or does not happen: a failed save or a rolled-back caller leaves neither the row nor its job. The job's `data` column keeps the job kind, its correlation chain and the committed event. Only the start of the runner waits for the commit. One runner per store (`committedJobs` in `committed-work.mjs`) runs the Ready jobs in table order (FIFO) on the organization scheduler (`runtime-clock.mjs`): on the next turn with the default scheduler, or when a test calls `runDue()`/`advance(ms)` on a manual one. A plug-in run then writes Locked and its final state in its own store transaction, so after Ready only the final state is observable: Completed/Succeeded (30), or Completed/Failed (31) with `message`, `friendlymessage` and `errorcode`. A succeeded job is removed when its step has `asyncautodelete`. While the Dataverse API is off the job row is only the queue entry and is removed when the run ends, so the portal tables keep their shape. A job whose step registration is no longer in the catalogue when it runs ends Failed (`LocalPluginAsyncUnavailable`). A web hook job is Locked while its POST runs, does not hold back the jobs after it, and is finished by `asyncoperationid` in a later transaction; if the row is gone by then, a `PLUGIN_ASYNC_JOB_MISSING` diagnostic is recorded. A job cancelled (statecode 3) before it starts does not run. Committed async runs are never dropped: past 100 queued runs (and each further 100) a `PLUGIN_ASYNC_BACKLOG` diagnostic is recorded and every run still executes in order; only the depth and per-chain loop guards (`PLUGIN_ASYNC_LIMIT`) skip runs. A root committed event starts its own chain, so the rows of one bulk commit never share one chain budget.

**Restart.** Ready jobs live in the state file. When an organization starts on a saved state, its backend (`createOrganizationBackend`) and `createOrganizationRuntime` resume them, and each runs exactly once; `backend.resume()` re-scans on demand. A web hook job left Locked by a stopped process stays Locked. `settleCommittedWork` (reload, stop, `backend.settle()`) waits for the queued jobs and for the store scheduler's due and running tasks, which include the `dataverse-async` jobs (BulkDelete, `systemJob`, background operations). With a manual scheduler, settle waits only for running work; Ready jobs wait for `runDue()`. A job waiting on a not-yet-due task of that scheduler (a connector retry pause, for example) is blocked: settle and close return without it, and the `advance(ms)` that makes the pause due finishes it. A job still Ready at close runs in the next runtime.

**Classic workflow background runs.** A classic workflow's background run (mode 0 trigger on create, update or delete) is a committed job of kind `workflow`: a commit stager writes its Ready asyncoperation row inside the triggering transaction, so a rolled-back write starts nothing, and the store's job runner claims it (Locked, In Progress), runs it like any classic run and completes it Succeeded, Failed or Canceled. The row carries `operationtype` 10 (Workflow) from staging to completion. Ready rows resume after a restart.

**Dataverse Functions and low-code plug-ins.** A custom API whose `fxexpressionid` names an `fxexpression` row (a Dataverse Function) evaluates its expression with the core Power Fx engine (see [Canvas apps, Power Fx](canvas-apps.md#power-fx)). Input parameters are named values; the result record fills the response properties. The function reads and writes Dataverse tables (`Filter`, `LookUp`, `Collect`, `Patch`, `Remove`, `CountRows`, `Sort`) as the calling user, never as SYSTEM, with the caller's privileges, row access and column security, and runs as one unit: an error after a write leaves no row behind. An `Error(...)` or another formula error value answers 400 `0x80040265` with the error's message. A write the data source refuses (a missing privilege, a column-security or validation refusal), also inside `ForAll`, answers that refusal with the same envelope the Web API gives, and the function's earlier writes are rolled back. Error values flow on through a formula and `;` chain (IfError and IsError handle them); an engine exception (a syntax error, an unknown name or function) ends the formula and rolls its writes back. An automated low-code plug-in (an `fxexpression` row with a message and a table) runs before the write as the calling user: `Set(ThisRecord.column, value)` or `Set(column, value)` changes any column of the row being written, whether or not the request named it; a change to a secured column the caller may not write refuses the write with the column-security error (403 `0x8004f502` on create, `0x8004f507` on update); `Error(...)` refuses the write with its message. With the engine explicitly disabled (`createPowerFxEvaluator({ engine: false })`) both answer 501 `PowerFxEvaluatorMissing`.

A Solution may define a Dataverse Function entirely in its sources: `fxexpressions/<uniquename>/fxexpression.xml` (root `<fxexpression uniquename="...">` with the fxexpression columns `fxexpressionid`, `name`, `expression`, `context`, `parameters`, `messagename`, `entitylogicalname` and `statecode` as child elements) holds the Power Fx expression, and the custom API's `customapi.xml` names it with `<fxexpressionid>`: either the id as text, a nested `<fxexpressionid>` id, or a nested `<uniquename>` of an fxexpression in the same Solution. The Function then evaluates through the Power Fx engine like a pack-seeded one; a custom API without `fxexpressionid` and without a handler keeps the default outputs. An fxexpression without `fxexpressionid` gets a stable id derived from its unique name. An fxexpression with `messagename` and `entitylogicalname` that no custom API names runs as an automated low-code plug-in. The exported layout of this folder was not captured from a live export; it follows the `customapis` layout. The `fxexpressions` folder is a Solution side folder: changing it refreshes the running simulator like `customapis`.

**Delegation.** Table queries in a formula are delegated to the store when every predicate is delegable for Dataverse: comparisons of a column with a value (also through `Upper`, `Lower`, `Left`, `Mid` and `Replace` of a text column), `And`/`Or`/`Not`, `IsBlank`, `StartsWith`, `in` (substring and membership), `Sort`/`SortByColumns` by a column, `First`, `LookUp`, `CountRows`, `CountIf`, and `Sum`/`Min`/`Max`/`Average` of a number column. Comparisons with `Now()` or `Today()`, currency columns, and `Right`/`Substitute` of a column are not delegated. Any other predicate reads the first 500 rows (the data row limit, `host.dataRowLimit`) and evaluates in memory, and the run reports the `POWERFX_DELEGATION` warning naming the table, the operation, the limit and whether rows were cut off.

Synchronous JavaScript handlers (step id and plug-in type) and original CLR steps share one plug-in `Depth` counter (`pluginExecutionDepth`, `enterPluginExecution` and `leavePluginExecution` in `plugin-clr.mjs`), so a chain that mixes JavaScript and CLR steps counts each nested level once. The cap is 8: a ninth nested level fails with `LocalPluginDepth` (400; "Plug-in nested execution depth exceeds eight." from a handler, "CLR nested execution depth exceeds eight." from a CLR step) and rolls back with the caller.

Handlers and CLR runs write plugintracelog rows according to `organization.plugintracelogsetting` (0 off, 1 exceptions, 2 all); the trace lines a handler writes through `trace(text)` form `messageblock`.

`TriggerServiceEndpointCheck` (bound to serviceendpoint) POSTs a probe to a contract 8 endpoint only when its URL is loopback, and answers 204 for any 2xx. With a messaging provider, a contract 2, 5 or 6 endpoint answers 204 when `providers.messaging.endpoints` maps it (nothing is sent) and 400 when it does not. Other contracts and non-loopback URLs get a 400 and are never contacted. The probe body, headers and error texts are unverified (LC-P7a). It sends no authentication value.

## Webhooks

A step whose eventhandler is a service endpoint with contract 8 (Webhook) posts Learn's `RemoteExecutionContext` JSON (27 properties, in the order of the documented sample) to the endpoint URL. The headers are `x-ms-dynamics-organization`, `x-ms-dynamics-entity-name`, `x-ms-dynamics-request-name` and `x-ms-correlation-request-id`. Authentication follows `authtype`: WebhookKey (4) sends `?code=<value>`, HttpHeader (5) adds the key/value pairs as headers, and HttpQueryString (6) adds them as query parameters. Above 256 KB, `ParentContext`, `InputParameters`, `PreEntityImages` and `PostEntityImages` are removed and `x-ms-dynamics-msg-size-exceeded` is sent. Learn's retry applies: 502, 503 and 504 get one more attempt. Each attempt has the 60-second timeout.

**Loopback only.** Mirage contacts an endpoint only when its URL host is `localhost`, `*.localhost`, `127.0.0.0/8` or `::1` (`isLoopbackUrl` in `dataverse-webhooks.mjs`, the one guard shared with `TriggerServiceEndpointCheck` and the asynchronous `odata.callback` check in `dataverse-async.mjs`). Any other URL (or a missing endpoint row) is never contacted. The step never counts or reports as delivered: a synchronous step lets the operation continue, and an asynchronous step writes a Canceled System Job (statuscode 32) with the message `Simulator: endpoint not contacted (loopback webhooks only)`. The dashboard counts it under `webhooks.notContacted`. A `WEBHOOK_NOT_CONTACTED` diagnostic records that the endpoint was not called. It names only the host, never the path, query or authentication value. Learn's own rule (ports 80 and 443 only) is not checked, so a loopback URL on another port is accepted. A host name that is not a literal address (such as `*.localhost`) is resolved before the POST, and the POST is refused unless every address it resolves to is loopback (`loopbackFetch`, in process and in the synchronous I/O bridge worker), so the step fails as an unreachable endpoint.

Contracts 2 (Queue), 5 (Topic) and 6 (Queue Persistent) go to the local message bus when the runtime has a messaging provider, which both hosts configure; `providers.messaging.endpoints` must map the endpoint, or the step fails with `SERVICE_ENDPOINT_UNMAPPED` (see [Messaging and outbox](messaging-and-outbox.md#service-endpoint-delivery)). Without a messaging provider, and for every other contract (Event Hub, ...), the endpoint is not simulated. A synchronous step is skipped with a `WEBHOOK_NOT_DELIVERED` diagnostic. An asynchronous step writes a Canceled System Job (statuscode 32) with the message "Simulator: endpoint not delivered (loopback webhooks only)". Neither is contacted.

A contacted loopback endpoint that answers outside 2xx is a real failure: a synchronous step fails with "Endpoint unavailable" and rolls back, and an asynchronous step leaves a Failed System Job (statuscode 31).

**Synchronous webhooks block.** A synchronous step waits for the endpoint inside the operation. On the asynchronous pipeline (every HTTP-driven write) the POST (`send`) is awaited in process before the next step runs. For an SDK call a plug-in makes (the synchronous SDK drive) the POST runs on the synchronous I/O bridge (`sync-io-bridge.mjs`), a worker thread the calling thread waits on. A 2xx lets the operation commit. Any other status, or no answer, fails it ("Endpoint unavailable"), and the write rolls back. Learn notes that the request already sent cannot be recalled: a step that posted before its operation rolled back records `SERVICE_ENDPOINT_SENT_BEFORE_ROLLBACK`, and one whose post got no answer but may have been delivered records `SERVICE_ENDPOINT_SEND_INDETERMINATE`.

**Asynchronous webhooks** are delivered after commit, in-process, and each run writes its System Job (see above). Learn's query for failures (`statuscode 31`, `owningextensionid`) finds them.

Not verified against a live environment, and marked `unverified` in the source: the stored `authvalue` format (LC-P6a: XML settings, JSON or key/value text are all read), the native error code and text of an unreachable endpoint (LC-P6b: 0x80040265), the value of the size header, the money, option set and collection shapes inside the payload (LC-P6c), and the codes of the registration errors for a web hook without a URL or with an authentication type other than 4, 5 or 6 (LC-P6d). A Solution step whose `<EventHandler>` names a service endpoint is delivered like a step registered through the API. The handler is a service endpoint when the export names it with `ServiceEndpointId` or `EventHandlerTypeCode` 4618, or when a bare `EventHandler` matches no plug-in type in the selected Solution layers (an exported plug-in step carries `PluginTypeId`/`PluginTypeName`). The endpoint row (`serviceendpoint`) comes from the organization, for example a pack's data; a step whose endpoint row is missing is recorded as `WEBHOOK_NOT_CONTACTED` (reason `missing-endpoint`) and its System Job is Canceled. Queue and topic contracts go to the message bus through `providers.messaging.endpoints`; a contract 8 web hook posts to its loopback URL.

An asynchronous step run that executes nothing (an unsupported registration, or a placeholder without a handler or mock) ends Canceled (`statuscode` 32) with the reason in `message`; it never reports Succeeded.

## Original assembly registration

Register exact exported step IDs in a trusted external data pack's `pluginRuntimes`. A descriptor contains `trust: 'execute-local-assembly'`, `root`, relative `assembly`, exact `typeName`, `sdkRoot`, relative `sdkAssembly`, `cacheRoot`, `serviceProfile` and `context`. Context requires evidence-qualified initiating-user, organisation and business-unit GUIDs. The profile requires an explicit execution-user GUID, evidence and table/operation grants; it does not inherit portal roles or administrator access. A null SDK service-factory caller requires an explicit local system-factory choice. Arbitrary impersonation is unsupported.

CLR preparation verifies confined regular files and hashes the original assembly, SDK, host source and generated host. No SDK download runs on portal startup. Workers cap protocol bytes, recursion, SDK calls, time and traces, and terminate only their owned host. Trusted original code can access the local machine; this process isolation is **not an untrusted-code sandbox**. Microsoft assemblies remain external to the toolkit distribution. Windows CI runs an actual compiled invented plugin against a pinned external SDK package; protocol-only tests do not substitute for DLL execution.

An explicit descriptor `persistentHost: true` reuses at most 32 owned hosts by prepared runtime, type and recursion depth. Each invocation constructs a fresh plugin instance, configuration and context; assembly static state remains process-local. Source and execution bytes are checked on every call, and deadlines, protocol bounds and SDK authorization still apply. A failed invocation closes its host. Campaigns call `closeClrHostPool()` in `finally`; a simulator closes its own pooled runtimes on shutdown. Default descriptors continue to use fresh hosts. Host reuse is a performance choice, not native evidence.

| Read pipeline | Synchronous Retrieve and RetrieveMultiple stages 10/20/40; typed query/input/output observers and serialized backend recording writes | Exact proprietary native permission-query transformation remains separately qualified |
| Context | Typed input/output/shared state, selected images, live nested ParentContext, correlation/depth, explicit portal transport Contact and Context2 flags | SDK properties outside the declared proxy contract fail explicitly |
| SDK | CRUD, Retrieve/RetrieveMultiple, typed linked Fetch/QE, nested joins/aliases and explicit per-table row grants; named Execute responses for these messages | Advanced filters, full-text queries, unknown request parameters and other SDK messages fail explicitly |
| SDK write pipeline | SDK Create, Update, Delete and Retrieve from a CLR plug-in (and the flow Dataverse connector) run the organization record pipeline after the explicit backend grants: state defaults, the synchronous record hooks (business rules, calculated and formula column refusal, currency, state transitions, duplicate detection, column security, rollup marking, cascade), audit columns naming the profile's systemuser (the organization SYSTEM user when the profile user is not an organization user), the organization row version and the Web API alternate-key answer (412 `0x80060892`). Retrieve and RetrieveMultiple apply the Web API read projection (computed columns, column security, masking) | An asynchronous pre-operation hook refuses the call (501 `SdkAsyncPreOperationUnsupported`); asynchronous post-operation remainders (audit association rows, real-time classic workflow runs) are at `contract`: see below. Associate/Disassociate and bulk messages keep their own relationship and bulk rules |
| Relationships | Associate/Disassociate SDK calls and named responses; exact imported schema/partner direction; endpoint, proposed-row and intersect-edge backend grants | Native source/context proof; ambiguous self-reference without source EntityRole metadata and parameter replacement remain gaps |
| Standard bulk | Explicit source-evidenced CreateMultiple/UpdateMultiple; typed Targets, Context4 aligned images, filtering, shared state, typed IDs and per-record exception details; atomic caller rollback | Native merged single/multiple ordering, elastic tables and other bulk messages are unqualified or unsupported; mixed registrations are rejected before writes |

| Lifecycle | Shared bounded plugin/flow chains, consumer isolation and coordinated drain/stop | Arbitrary external work and durable cloud-service scheduling are not implemented; flow Recurrence triggers run on the local scheduler ([operations](operations.md#execution-boundary)) |

An SDK call from a plug-in is synchronous: it runs inside the store's synchronous plug-in pipeline. Every record hook is called inline and in order, so the synchronous rules refuse or change the write exactly as on a Web API request, and a refusal rolls the SDK call back. A pre-operation (`beforeWrite`) hook must answer synchronously: one that answers a promise (an async-only Power Fx adapter behind an automated low-code plug-in, attachment bytes routed to a storage provider) refuses the call with 501 `SdkAsyncPreOperationUnsupported`, naming the hook's module, inside the call's savepoint and before anything is stored. A virtual table without a provider refuses the SDK write with 501 `VirtualProviderMissing`, as the Web API does; a provider operation runs after the SDK call's store write as the main operation and mirrors its row inline when it answers synchronously; the SDK call uses only the provider's declared `createSync`/`updateSync`/`deleteSync`, and without it answers 501 `SdkAsyncPreOperationUnsupported` before any provider call, leaving the local row unchanged; an automated low-code plug-in with a synchronous adapter (`evaluateSync`) changes the SDK-created row inline. A post-operation (`afterWrite`) hook that returns a promise has an asynchronous remainder that finishes after the SDK call returns, outside the call's savepoint; it is never awaited by the call and never reported as its success. A remainder that fails produces an `SDK_DEFERRED_EFFECT` diagnostic (`entity`, `operation`, `message`). SDK `Retrieve` and `RetrieveMultiple` (and FetchXML) take the `UnMaskedData` request parameter (exact case, a boolean), which unmasks under the same `CanReadUnmasked` rule as the Web API (Learn optional-parameters#return-unmasked-data). The service's `profile.pipeline` states these levels: `behaviour` for the write rules and read projection, `contract` for asynchronous hook effects. Without an organization on the store (no Dataverse organization runtime), the service writes the store directly and `profile.pipeline.level` is `inventory`.

Associate and Disassociate run one association pipeline (`dataverse-records.mjs` `associateInternal` / `disassociateInternal`) from the Web API `$ref` routes, the SDK service (and so the flow connector's AssociateEntities / DisassociateEntities) and the portal `/_api` `$ref` routes: appendTo on the row and append on each related row (the Web API caller; the SDK's explicit grants and the portal's table permissions are checked by their own callers and by the store write), the `beforeWrite` and `afterWrite` record hooks once per related row (audit 33/34 rows, security rules), and the Associate/Disassociate plug-in stages 10, 20 and 40 around the relationship write (the SDK service's own `executeAssociation` runs the stages with its grants).

System output parameters are populated once at the main-operation boundary, before PostOperation; Create does not expose its system `id` in PreValidation or PreOperation. Custom values survive ranked CLR steps, and an intervening project read handler updates the current Retrieve or RetrieveMultiple result without discarding custom outputs. Final synchronous output values reach the SDK caller's named response `Results`, including replaced Create `id`, CreateMultiple `Ids`, removed keys and supported typed custom values. Direct Create uses the installed SDK's missing-`id` default (`Guid.Empty`); a mistyped named output retains its raw value and the SDK getter throws its own type error. These are local documented-contract regressions with actual compiled invented DLLs, not native fixture qualification. See Microsoft's [execution context reference](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/understand-the-data-context).

For synchronous Create, Update and Delete, later CLR stages access PreValidation shared variables through `ParentContext.SharedVariables`. PreOperation and PostOperation share their own collection; nested SDK requests retain the incoming ancestor context and request depth. A later operation on a saved row starts a fresh frame. Original invented DLL regressions cover these documented contracts; native context comparison remains separate. `RetrieveExchangeRate` has no local message adapter.

The private response handoff is synchronous and scoped to one exact store, message, table and opaque SDK invocation token. Nested SDK requests have separate frames; bare project/flow operations, cascade children and later asynchronous work cannot overwrite the initiating SDK caller's results. Captures clone final values and are removed after success or failure. This is a correctness mechanism for trusted local code, not an untrusted-code isolation boundary. DataStore and flow row/bulk return shapes remain unchanged; no native WebAPI response-envelope behavior is inferred. Retrieve/RetrieveMultiple context keys `BusinessEntity`/`BusinessEntityCollection` are mapped to the installed SDK response keys `Entity`/`EntityCollection`. Conflicting context/SDK aliases require an explicit adapter and fail diagnostically. Unsupported SDK messages, unsupported value types and changed read identities retain their existing explicit limitations. See Microsoft's [SDK message reference](https://learn.microsoft.com/en-gb/power-apps/developer/data-platform/org-service/use-messages).

A default `InvalidPluginExecutionException` from the supplied Microsoft SDK carries a CLR source HRESULT. Mirage preserves that raw value in `sourceException.errorCode` and maps the default `0x80131500` to the Dataverse `IsvAborted` fault code `0x80040265` for HTTP inner errors and nested SDK faults. Explicit nondefault codes remain unchanged. Actual invented DLL HTTP tests cover the default, explicit custom code, unchanged unrelated exception behavior and a nested `FaultException<OrganizationServiceFault>` caller. This does not establish equality between the direct Dataverse HTTP envelope and the Power Pages portal wrapper, or qualify other native exception shapes. See Microsoft's [plugin exception guidance](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/best-practices/business-logic/use-invalidpluginexecutionexception-plugin-workflow-activities).

Imported `multiselectpicklist` columns use `OptionSetValueCollection` in Targets, entity images and SDK reads. Stored arrays or comma-separated strings retain their selected option integers; SDK writes accept source-typed Int32 option arrays and validate declared options before mutation. Untyped arrays remain unsupported deep writes. Original DLL tests cover Target/image typing and SDK Update/reload; native precision, formatting and query comparisons remain separate. See Microsoft's [choices column reference](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/multi-select-picklist).

Source-declared Float/Double columns retain `System.Double` for fractional and integral values in Targets, images, SDK reads and typed aliases. Original CLR writes, shared variables and output values carry an explicit finite Double wire value so that an integral Double does not become an Int32 on the next step. Nonfinite values fail explicitly. Actual invented DLL casts qualify these local contracts; native aggregate precision and overflow responses still require separate comparison.

Local OData-to-SDK query construction is a limited local adapter. It is not evidence of the proprietary Power Pages permission-query transformation. Internal SDK FetchExpression input remains FetchExpression; QueryExpression retains its typed nested LinkEntity/criteria/columns tree. Portal Fetch reads apply the modeled permission compiler before observers; the supported scalar portal OData adapter exposes modeled expanded FetchExpression, with its transport qualification recorded separately. Supported linked execution internally uses the local FetchXML evaluator, with typed AliasedValue results and Entity.Id independent of selected Attributes. Unsupported advanced shapes fail instead of returning altered SDK types. Invented original-DLL tests prove these local contracts separately from authorised native capture.

Bulk execution also requires `serviceProfile.bulkTables` entries with an exact logical `entity`, `tableType: 'standard'`, nonempty `evidence` and explicit `messages` (`CreateMultiple`, `UpdateMultiple`). This project assertion must come from captured table/message metadata; it is never inferred from a table name. CLR bulk handlers can replace the pre-operation Targets attribute collections while preserving table/count/existing identities. PostOperation changes are not persisted. Association parameters remain immutable in the local adapter. The [bulk plugin reference](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/write-plugin-multiple-operation) documents Targets, Context4 images and submitted-column filtering; the [relationship SDK reference](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/org-service/entity-operations-associate-disassociate) distinguishes relationship schema names from navigation properties. These documented contracts and invented DLL tests do not establish native business-source equality.

## Configure source facts

PAC can export an SDK message ID without its name. The Create, Update, Delete, Retrieve and RetrieveMultiple ids are platform constants Mirage knows; for other messages supply `observed.sdkMessages` entries with the exact ID, name and evidence from your environment. Mirage does not guess the operation from a step label.

To connect a supplied C# project, map an exact exported type name through `observed.pluginSources`:

Use the site's `mirage.observed` block in a Lense catalogue, or that portal's `observed` block in a Mirage project manifest.

```yaml
observed:
  evidence: Plugin sources and SDK message names verified for this project.
  pluginSources:
    Vendor.Plugins.CustomerRules:
      path: components/Plugins/CustomerRules.cs
      evidence: Type declaration matches the exported PluginType name.
```

Catalogue paths resolve from `sourceRoot`; project-file paths resolve from that project directory. Mappings must point to regular `.cs` files within the trusted root. Exported assembly and type metadata remain available when source code is absent.

## Model a write

A mock response body can change submitted values during stage 10 or 20:

```json
{"target":{"displayname":"Normalized value"}}
```

To test rejection, use:

```json
{"error":{"message":"The supplied value is invalid."}}
```

Project packs register `pluginSteps` handlers by exact step ID. A synchronous handler receives `step`, `entity`, `operation`, `stage`, `target`, `record`, `previous`, `identity`, `changedAttributes` and `reject(message)`. Return `{target:{...}}` to apply a patch. Context records are cloned; editing them alone does not change the store. Async handlers are rejected. Stage 40 and Delete handlers cannot patch the target.

Local Create, Update and Delete run supported synchronous stages in stage/rank/ID order. Update filtering checks submitted columns, including unchanged values. The table-level Create grant gate precedes all handlers. Create then runs stages 10 and 20, declarative rules and their secondary effects, the row-scoped permission check, then stage 40. Scoped denials report the permission name, scope and relationship in their details and runtime diagnostic. A row-scope denial revokes this request’s independent PreValidation SDK writes to prevent a denied portal write from leaving durable side effects. This is a local portal-permission boundary, not Dataverse security-check timing: Microsoft documents initial PreValidation before Dataverse's own security checks. Mirage defers its row-scope check so local rules can establish a relationship; this does not establish that a hosted portal invokes plug-ins for an equivalent denied request. For other rejections, top-level PreValidation SDK writes commit independently and remain saved after a later caller rejection; nested PreValidation and stages 20/40 participate in their caller's transaction. Each asynchronous SDK request is independent. These boundaries are tested with original invented DLLs; source-qualified native comparison remains a separate obligation. See Microsoft's [event framework](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/event-framework), [database transactions](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/scalable-customization-design/database-transactions) and [registration reference](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/register-plug-in).

The [demo plugin project](../../examples/project/components/DataversePlugins/README.md) includes C# sources, eight exported registrations and matching local models. Use [project tests](data-packs.md) to compare your model with authorized live execution.

Source-declared lookup GUIDs are supplied to original CLR plugins as SDK `EntityReference` values when the exported lookup metadata names exactly one target table. This applies to Targets, images and SDK retrieval, including a source-defined self-referencing relationship. Explicit typed references retain their logical table; a raw GUID with missing or multiple lookup targets fails with `LocalPluginSdkUnsupported` instead of selecting a table. Compiled invented DLL regressions cover lookup casts and named association responses. See Microsoft's [EntityReference contract](https://learn.microsoft.com/en-us/dotnet/api/microsoft.xrm.sdk.entityreference?view=dataverse-sdk-latest) and [lookup target metadata](https://learn.microsoft.com/en-us/dotnet/api/microsoft.xrm.sdk.metadata.lookupattributemetadata.targets?view=dataverse-sdk-latest).

Original local CLR shared values preserve byte arrays, explicitly modeled primitive and SDK arrays (including null entries and jagged string arrays), `EntityReference.KeyAttributes`/`RowVersion`, and `EntityCollection.EntityName`/`MinActiveRowVersion`/`TotalRecordCountLimitExceeded`. The installed SDK known-type catalogue and compiled typed readers guide these codecs. Unknown array contracts fail explicitly; metadata/label SDK contracts and request/response collections are not supported. Preserving reference metadata does not implement alternate-key backend CRUD.

Supported named SDK requests accept the optional `tag` string (bounded to 8 KiB locally). The tag reaches original CLR shared variables, survives PreValidation parent separation and inherits through nested shortcut service calls. Descendant replacement and plugin mutation fail before a changed tag is propagated; owned request state is restored on failure. Original-DLL regressions exercise `DeleteRequest.Parameters["tag"]`, all three Delete stages and a nested Create. Native fault HRESULTs for prohibited tag changes and portal Web API optional-tag transport require separate qualification.

Configured read mocks can include the optional result metadata above. Pure mock or handler read steps preserve typed results for direct and named original SDK callers, while ordinary reads keep their existing projections. Actual loopback admin regressions also verify that choosing mock or disabled for an original plugin prevents its dependency calls and launches no additional CLR host. These controls do not predict arbitrary external network behavior.

## Read recording and portal contexts

HTTP and Liquid read providers enter a serialized `DataStore.readOperation()` boundary before invoking local read plugins. Pure reads preserve the state revision and file; synchronous SDK recording writes use explicit backend grants, save successfully completed requests and publish their committed events. A top-level read is outside a database transaction at stages 10, 20 and 40, so a later observer or query rejection retains earlier independently completed SDK writes. A read called from a transactional CRUD plugin inherits that transaction. Direct synchronous reads without a serialized request boundary continue to reject original SDK writes. These contracts follow recorded lab context patterns and invented original DLL regressions; durable collector or arbitrary hosted pipeline parity is not implied.

An explicit trusted portal transport option supplies `IsPortalsClientCall` and `PortalsContactId` from the active local Contact. User roles alone do not set these properties. Nested SDK operations clear both properties while retaining the live parent context and correlation. Each local request frame supplies a stable generated RequestId and empty SecondaryEntityName for the supported single-table CRUD/read messages. Local GUIDs and timestamps are local provenance rather than copies of native platform values. Microsoft's [Context2 reference](https://learn.microsoft.com/en-us/dotnet/api/microsoft.xrm.sdk.ipluginexecutioncontext2?view=dataverse-sdk-latest) describes these portal properties.

An original runtime descriptor may explicitly list `sdkCallerProfiles` for known SDK factory callers. Each identity requires its own evidence and table/operation grants. A nested SDK pipeline uses that requested execution identity, preserves the initiating ancestor identity and restores the previous frame after completion; unknown callers still fail. An exported run-as step can independently bind `context.executionUserId`. This does not infer Dataverse impersonation privileges from portal roles.

Evidence-qualified `context.interfaceVersion: 7` supplies environment ID, tenant ID, application-user status and user-agent presence, with a local placeholder for the withheld user-agent value. Nonbulk Context4 image collections preserve empty collections or a single registered image set. Explicit portal input observations support `AppModuleId`, `IsAppModuleContext` and `IncludeAnnotations`; an observed empty Fetch paging-cookie convention can also be selected. Default descriptors keep Context4 and do not invent those observed properties. Native `SecondaryEntityName` can be supplied as a context observation.

An explicit mapping `sdkRowVersionColumn` preserves a source integral row version independently of selected SDK Attributes. The original CLR transport retains `Entity.RowVersion` in both directions. Native snapshot replay can supply actual version metadata from a read-only projection or ETag evidence. Local CRUD does not predict the organisation-wide native version sequence or claim native optimistic-concurrency execution.

Fetch aggregate `count` and `countcolumn` aliases carry Int32 values independently of the original column type. Grouped lookup names and choice labels use declared primary-name metadata, source target rows and option labels; missing metadata does not produce an invented name. Supported groupby lookup aliases include the native companion name attribute and formatted values. Culture-sensitive numeric, date and currency display contracts still require their source settings and separate qualification.

## Read query registration and provider metadata

An explicitly unfiltered synchronous `RetrieveMultiple` step can observe every
supported queried table. An exported empty SDK filter or explicit `none` binding,
or a project's exact native null-filter witness, establishes this scope. Missing
and unresolved filters remain unsupported. The execution context retains the
actual queried table as `PrimaryEntityName`; scope is never substituted into
runtime context. Registration acceptance does not establish that a particular
platform table invokes custom processing. Native callbacks on one supported
table do not qualify tables which emitted no callback evidence.

SDK QueryExpression paging/count controls retain the authored QueryBase in every
observer stage. The execution adapter requests totals only when the caller sets
`PagingInfo.ReturnTotalRecordCount`; pure SDK Fetch without an explicit total
count request returns `-1`. Provider EntityCollections carry the actual root
logical name and the source-qualified default minimum active row version `-1`.
Plugin-created collections keep their SDK constructor defaults. Explicit minimum
active row version requests require a qualified provider, and fail diagnostically
otherwise. Counts over the configured maximum preserve the limit-exceeded flag;
native count-limit campaigns remain a separate qualification gate.

Trusted replay descriptors may set `context.operationCreatedOn` with a canonical
UTC timestamp (up to seven fractional digits) and bounded
`operationCreatedOnEvidence`. This is recorded framework request-envelope
metadata, not an expected query/data result. An existing frame timestamp wins;
otherwise the explicit timestamp is preserved without rounding .NET ticks. The
runtime uses its clock when no timestamp is supplied. This supports independent
historical checks of source plugins that compare their immutable intent time to
the framework operation time.

Fresh and pooled CLR hosts bind the owning Node process PID and actual .NET
process birth time. A background host watcher terminates that host when its
exact owner exits, including an abrupt process kill while plugin code loops
without returning. Reusing a PID with a different birth time cannot keep the
host alive. Ordinary cleanup still closes owned hosts and verifies their absence.
