# Sources and bootstrap

The importer accepts standard portal exports, enhanced unpacked component XML and short-key `.powerpages-site` code-site exports. It uses record types and IDs, exported page/template relationships, languages, settings, snippets, forms/lists, permissions and web-file metadata. Ambiguous or incomplete inputs produce diagnostics; `serve` rejects sources with no recognized pages.

Solution roots contribute table/entity-set identities, columns, relationships, views, system forms, choices, environment variables and permission relationships. Roots are a set layered in dependency order; explicit ordering is an opt-in and doctor reports disagreement. Source caches are keyed by physical file properties and implementation fingerprints; local state and source provenance remain distinct.

`importSolutionData()` (also its `schema`) and `importSolutionMetadata()` expose `contentFingerprint`, a SHA-256 of selected layer order, exported logical Solution name/version, normalized relative filenames and file byte hashes, qualified by LCID. The files are the scanned metadata documents plus every file below the top-level `Workflows`, `WebResources`, `customapis`, `fxexpressions`, `duplicaterules`, `Controls`, `powerpagecomponents` and `PluginAssemblies` folders (folder names match without case), from unpacked directories and Solution ZIPs alike, so workflow XAML, cloud-flow JSON, web resources, custom APIs, Power Fx expressions, duplicate rules, PCF controls, portal components and plug-in assemblies are covered; other files in a layer are not. Moving or renaming the checkout root preserves it; changing bytes, a relative filename, logical Solution identity or layer order changes it. Layers without a manifest use their ordered position, not the checkout directory name. The existing `fingerprint` retains physical source identity for location-bound caches. Content identity describes imported Solution sources, not deployed state, project observations or separately mapped plugin source files.

Bootstrap preserves configuration but creates no real business records. `data scaffold` uses metadata to generate deterministic rows; external packs supply project behavior. Watch reload refreshes changed configuration and metadata without overwriting authoritative local state. On both hosts a source reload re-registers the Solution source modules (custom APIs, duplicate rules, classic workflows with their activation rows, plug-in registrations) from the reloaded sources; rows a previous seed wrote whose definition is gone are removed (state `dataverse.sourceSeeded` records what each seed wrote). The diagnostic `SOURCE_EXTENSIONS_REFRESHED` lists the changes. On the Power Pages host every Solution re-scan (a source reload or a deployment profile change through `PUT /_sim/api/environment/profiles`) is checked against the last accepted scan. A scan with an error that scan did not have is rejected with `SOURCE_RELOAD_REJECTED` (409): the portal, Solution metadata, environment variable definitions and registrations stay as they were, the rejected scan never becomes the baseline, and a reload records `RELOAD_FAILED`. A Solution may define a Dataverse Function in its `fxexpressions/<uniquename>/fxexpression.xml` files (see [Dataverse plugins](dataverse-plugins.md)); the `fxexpressions` folder is a Solution side folder, so changing it refreshes the running simulator like `customapis`. State writes use the integrity protocol described in [state integrity](state-write-integrity.md).

Project files declare portals, Solutions, reference origins and explicit pack modules. Site-specific `observed` settings with evidence supply behavior that cannot be exported, such as a deployment-specific login path or response header. Do not use customer names as runtime selectors. Inspect `inspect`, `bootstrap-report` and `portal-matrix` JSON for imported components, unresolved tables/fields and missing sources.

## Solution inventory

Some Solution components are read and listed but never hosted or executed. `scanSolutionSources()` returns them as `scan.inventory`, and `loadOrganizationSources()` returns the same list as `inventory`. Each record has this shape: `{ component, componentType, id, name, version, solution, layer, source, format, dependencies: [{ component, name }], level, reason }`. `level: 'inventory'` means the component is listed but nothing runs it. `level: 'behaviour'` means another importer executes the component and this record only lists it. Inventory never creates a Dataverse table or row. A strict Lense audit never counts it as coverage, and `lense list --json` shows it per site as `inventory.counts`.

A connector whose compilation has a blocking diagnostic (`CONNECTOR_OPENAPI_VERSION_UNSUPPORTED`, `CONNECTOR_AUTH_UNSUPPORTED`, `CONNECTOR_POLICY_UNSUPPORTED`, `CONNECTOR_SCRIPT_MISSING`, `CONNECTOR_SCRIPT_OPERATION_UNKNOWN`, `CONNECTOR_POLICY_OPERATION_UNKNOWN`, `CONNECTOR_MEDIA_TYPE_UNSUPPORTED`) carries it as an error, so its preflight row `connector:<name>` is `unsupported` with that code as reason. Mobile offline profiles (component type 161, `MobileOfflineProfiles/` or `<MobileOfflineProfiles>`) are listed as inventory and reported by `model-driven:offline/<profile>` rows, satisfied when the simulator evaluates every item's filter (see [model-driven client API](model-driven-client-api.md)). Imported roles and profiles produce no preflight row; an unread one is reported `unsupported` with its reason.

Codes come from the [solutioncomponent `componenttype` choices](https://learn.microsoft.com/power-apps/developer/data-platform/reference/entities/solutioncomponent). Components stored as rows of solution-aware tables, such as connection references, app actions, bots and plug-in packages, have no fixed code in that list, so their `componentType` is `null`. Folder names match regardless of case. A scan emits each inventory diagnostic once per component kind and layer. These diagnostics carry `inventory: true` and do not block reuse of an unchanged scan.

The scan also merges each layer's records:

- One record is kept per component and name. Customizations.xml, `.meta.xml` and `.msapp` describe the same canvas app.
- `Solution.xml` `RootComponents` mark records as `root: true`. A root component without a source file becomes a record with `sourceMissing: true`.
- `MissingDependencies` add `{ missing: true }` dependencies to the dependent record.

Canvas `.msapp` payloads up to 32 MiB (the Dataverse canvas app `document` limit) are parsed by `canvas-source.mjs`. The parse records screens, components, data sources and formula text in `record.canvas`; the scan evaluates nothing, the canvas runtime does ([Canvas apps](canvas-apps.md)). A ZIP layer keeps an `.msapp` entry as name and size, and inflates it only within that limit.

**YAML source-control format.** A directory with `solutions/<name>/solution.yml` is a Dataverse Git integration or `pac solution clone` repository ([format reference](https://learn.microsoft.com/power-platform/alm/solution-source-control-yaml-format)). The scan reads one layer per solution, with `format: 'yaml'`, named by its `UniqueName`; each layer holds the component paths its `solutioncomponents.yml` lists (every component folder when the file is absent). `rootcomponents.yml` and `missingdependencies.yml` feed the same root-component and missing-dependency rows as `Solution.xml`. One adapter reads the YAML files by the XML-to-YAML element rule Learn shows for `publisher.yml` (element keys, `'@name'` attributes, lists for repeated elements) and hands the schema parser the classic shape: table folders (`entities/<table>/entity.yml`, `attributes/`, `formxml/`, `savedqueries/`) become tables, columns, forms and views; `optionsets/` and `entityrelationships/` files become global choices and relationships; environment variable definitions and values are imported. A YAML file that yields no component is `SOLUTION_YAML_COMPONENT_NOT_IMPORTED` and an unparsable one `SOLUTION_YAML_INVALID`; a solution that loads nothing is `SOLUTION_YAML_EMPTY`. All three block strict preflight. Modern flows (`modernflows/`), canvas apps, connectors and connection references are listed as inventory; Learn does not describe the `modernflows/` file layout, so cloud flows from a YAML repository are not run.

**Connection references from Solutions.** Customizations.xml `<connectionreferences>` and YAML `connectionreferences/` become `importSolutionData().connectionReferences`, as `{ logicalName, displayName, connectorId }`, where a later layer wins. Each one seeds a `connectionreference` row with `connectionid: null`. A deployment-profile `ConnectionReferences` entry with the same logical name binds the row: its `ConnectionId` and `ConnectorId` win. Each Solution reference without a binding reports `SOLUTION_CONNREF_UNBOUND`.

**Source graph.** `loadOrganizationSources()` also returns `graph`, a read-only index built from the loaders' results by `buildSourceGraph()` in `source-graph.mjs`. It holds layers, tables, environment variables, connection references, forms, views, workflows, inventory records and, when a portal is given, its pages. `graph.resolve(kind, key)` returns the node in effect: the node from the later selected layer wins. `graph.requirements()` lists `{ id, kind, source, status, reason }` rows, where `status` is one of the following:

- `satisfied`
- `missing`: an unbound connection reference, an environment variable without a value or default, or a missing dependency that no selected layer provides
- `placeholder`: canvas apps
- `unsupported`: other inventory-level components
- `disabled`: inactive workflows

`graph.summary()` counts nodes per kind and level. `graph.fingerprint` hashes node ids, layers, versions and levels, never paths or values. The public `loadSourceGraph()` builds the same graph from Solution roots (see [public API](../../docs/public-api.md)).
