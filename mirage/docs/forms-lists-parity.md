# Forms and lists

Mirage builds native basic/multistep forms, lists, lookups, subgrids and notes from exported portal configuration and Solution form/view metadata. Standard/enhanced record fields normalize into a common model. Missing managed metadata is reported and may use an explicit local fallback; it is not inferred from a customer name.

The client adapters provide platform-shaped form events, validators, date/picklist controls, lookup dialogs, grids, paging, actions, notes/attachments and session-sensitive requests. Permissions are checked through the local data layer. Generated form fields and unsupported controls retain diagnostics for inspection.

Basic form Activate/Deactivate buttons follow exported `Actions` settings. Mirage resolves the record again from the configured query, current user or related-record source, checks read/update permissions, and changes only state/status in an atomic local write. Status values require exported state/status metadata; unsupported actions, unresolved metadata and action filter criteria retain diagnostics. Confirmation, labels and redirects use source settings, while managed dialog placement and filter behavior require reference evidence. Multiple forms with repeated button IDs dispatch through the button's full WebForms name.

Native subgrid quick-find visibility follows its exported FormXml flag. Native PCF fields require explicit portal attribute enablement and a supported desktop binding. Native list/subgrid PCF hosting retains diagnostics and the native grid fallback; dataset hosting uses explicit Liquid table/view bindings. See [code components](code-components.md) for the host and save boundary, and [coverage](../../docs/coverage.md) for remaining limits.

When a form redirects after saving, configure its appended record-ID parameter explicitly. Mirage preserves the exported redirect name and query settings; it does not supply a missing `id` name. Check the resulting page and saved record, not only the successful submit response. See [basic form success settings](https://learn.microsoft.com/en-us/power-pages/configure/basic-forms#on-success-settings).

A Power Pages export is a WebForms portal, so native forms post the page back by default: the browser submits URLencoded (multipart with the attach-file control) successful controls to the page's form action, including modal documents and auto-generated steps. `observed.nativeFormTransport: "json"` selects the local JSON form endpoint instead. Mirage resolves the page's current forms, actor, record and advanced-form session before decoding the exact WebForms target; posted record or session controls cannot replace that context. Source success settings choose an inline HTML response or the existing redirect target. Native required, format, range and length errors render HTML with status 200. Failed atomic basic-form writes also re-render the form with escaped posted values and `#MessagePanel.alert-danger`; their original error code/text remain in diagnostics and request evidence. CSRF, malformed/forged controls, inaccessible pages and errors before the write provider keep their error status. The JSON endpoint retains its error status and adds an error postback presentation; the browser reloads the same document with posted controls and the visible error panel. Advanced forms retain their existing LiquidServerControl inline save-error contract. Auto-generated steps render one tab per page: Next and Previous post the page back, the tab index and the earlier tabs' values travel in `__VIEWSTATE`, and the last tab's Insert saves them all. A multistep step with `adx_referenceentityshowreadonlyform` renders the referenced record's read-only form (`ReadOnlyFormView_<table>`) before its own form. A control the platform cannot render (an inline web resource, a quick view on a postback-rendered step, a control whose id the read-only form already rendered) stops the form at its cell with the platform's error alert and ends the server form's content there, as the live portal does. File selections cannot survive a browser reload and must be selected again.

Modal and quick-view documents use a local pending image to release the browser's actual
`load` event after jQuery's ready promise and one more macrotask. Without jQuery the image
is released at DOMContentLoaded; a throwing ready callback does not block other callbacks.
The blocker fails open after five seconds with `FRAME_READY_TIMEOUT`, and runtime shutdown
closes owned blockers. `FRAME_LOAD_ORDERING` records the release ordering. This adapter
stabilizes local resource timing; it does not establish identical timing on every deployment.
An evidenced `observed.modalLoadOrdering: immediate` opts out.

Native checkbox postbacks follow ASP.NET's successful-control semantics: a non-empty
posted value (including a project script's custom value) saves Boolean `true`; an empty
or omitted value saves `false`. Only editable checkboxes rendered by the selected form
participate. Read-only, disabled and off-tab controls are not cleared. Boolean radio/select
controls decode their `1`/`0` values and reject invalid text; the JSON form API requires
typed Boolean values. These rules do not coerce arbitrary direct DataStore writes.

Permission failures use the existing portal access-denied wording. Other write failures use
the toolkit fallback "An error occurred while processing your request. Please try again."
until the site supplies `observed.formSubmissionErrorMessage` with `evidence`. This is plain
text, escaped in HTML; it does not reproduce a native localized message or exception stack.

Native form redirects include `Content-Type: text/html; charset=utf-8`, matching the captured response header. The redirect body is not qualified by that header comparison.

Systemform selection preserves both the literal enclosing FormXml group (`formType`; a document without a declared group takes its `FormXml/<group>/` directory, as SolutionPackager writes one directory per form type) and an explicit numeric `<type>` (`systemFormType`). The numeric value takes precedence: Dataverse documents Main as `2` and Card as `11` in the [SystemForm table reference](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/reference/entities/systemform). A named portal form selects an eligible Main rather than an earlier same-name Card. If matching exported forms have known non-Main types, Mirage reports `SYSTEMFORM_INELIGIBLE_TYPE` and does not invent an approximated editable layout. Missing and untyped legacy exports retain their existing approximation behavior; unknown future group literals are preserved without a guessed numeric type. This local unresolved-layout behavior is not a claim about the exact native Card-only error response.

The selected metadata LCID applies to form names, field labels, tabs, sections and nested
quick forms. It also applies to the existing local label fallback after tab-name matching;
this does not redefine or certify native Tab Name selection. When that LCID has no exported
label, the existing first-exported-label fallback remains in place.

The [Power Pages Data workspace documentation](https://learn.microsoft.com/en-us/power-pages/configure/data-workspace-forms) describes Main as the supported portal form type. Microsoft also documents a [duplicate-name issue across form types](https://learn.microsoft.com/en-us/power-pages/known-issues) that can cause the wrong native form to render. The captured Main/Card comparison qualifies the observed field selection for the tested site; it does not establish every native duplicate-name retrieval order.

Multistep imports preserve the exported `Start Step`, every owned step, and explicit next/condition-failure references. References to another form's step retain that record and emit an informational ownership diagnostic; this does not qualify native cross-owner execution. Condition and redirect steps retain their raw settings, localized values, scripts and source references rather than being treated as load forms. Missing or inactive referenced records remain explicit dependencies. A missing declared initial step cannot select an unrelated later layout or redirect. Layout approximation retains the declared start and reports each absent Dataverse layout; it is not exact layout parity.

Microsoft documents [Start Step as the first step, which cannot be Condition](https://learn.microsoft.com/en-us/power-pages/configure/multistep-form-properties), and [condition branches and step reuse restrictions](https://learn.microsoft.com/en-us/power-pages/configure/multistep-form-steps). Mirage reports an unsupported Condition start instead of rendering invented controls. During local submissions, a missing referenced next step cannot become terminal success, and a repeated condition chain cannot become a resumable load step. Direct missing references are checked before writes; branch checks use the saved row inside the provider's existing write unit and precede session/history updates. Local transaction rollback is verified for local providers. Native data commits and error responses for broken step configuration remain unqualified; a provider without transactions may commit its write before the branch check fails.

Condition numeric comparisons retain saved Int64/Decimal digits and numeric literal digits through the exact arithmetic helpers. Adjacent values beyond JavaScript's integer precision, and decimal fractions that would collapse through `Number()`, select distinct local branches. Conditions use the provider's saved row, including provider changes, before updating session history. String, null, boolean, wildcard and existing numeric-string coercion remain covered by regressions. This establishes local precision correctness; Microsoft documentation does not define native numeric coercion/precision, which still needs comparison captures.

The [conditional step documentation](https://learn.microsoft.com/en-us/power-pages/configure/add-conditional-step) includes the unquoted multiword example `new_name = Jane Doe`. Mirage accepts these values up to a logical operator or group boundary, preserving their spaces, alongside quoted values and wildcard operands. Missing values, unbalanced groups, mismatched/unterminated quotes and adjoining quoted/unquoted values produce explicit unsupported-expression errors. Exact native whitespace, coercion and error-response behavior remain unqualified.

The postback adapter retains exact decimal/Int64 tokens, declared repeated controls and omitted controls, and converts source textarea line endings to LF. Files post with the page only through the attach-file control's multipart form; URLencoded file submission is explicitly rejected. ASP.NET viewstate and event-validation blobs are not emulated. A native fixture's route, saved values, validation response, request fields, browser lifecycle and restoration still need separate reference comparisons before claiming transport parity.

Project tests should assert their own rendered labels, relationships, native actions and backend results using an explicitly registered dataset. Core tests exercise invented minimal forms and loopback requests. A business flow passing locally establishes that simulation scenario only; compare reference DOM/network behavior before calling it platform parity.
