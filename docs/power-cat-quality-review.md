## Verified product facts and diagnostic policy

[The current Microsoft Web API overview](https://learn.microsoft.com/en-us/power-pages/configure/web-api-overview), independently read during this review and updated 2026-10-09, confirms that wildcard field settings are deprecated and affected requests fail. It documents view-based columns, their union with explicit fields, and the minimum supported site version of 9.8.8.x. It also distinguishes setting logical names from request EntitySetName values. This is configuration evidence, not evidence of a deployed site version or successful runtime request.

[Create and assign web roles](https://learn.microsoft.com/en-us/power-pages/security/create-web-roles) confirms only one anonymous and one authenticated default role per site. [Site Checker performance](https://learn.microsoft.com/en-us/power-pages/admin/site-checker-performance) supports output-cache diagnostics and advisory thresholds of more than 500 active web files or 100 roles. Its tracking checks describe functionality retired for newer sites; applying them indiscriminately would add noise.

The implemented record rules report unsupported wildcard fields and incomplete explicitly enabled Web API configuration as errors. View-based configuration produces a verification hint, including its published view and site-version prerequisites. It never produces a false missing-explicit-list error. Ambiguous duplicate settings and environment-backed values are unresolved rather than interpreted as runtime facts. Duplicate role defaults are checked per site, inactive records are ignored, and repeated representations of one identity are not counted twice.

Explicit inner errors, disabled default HTML encoding, disabled shared output caching and literal identity-secret settings produce reviewable warnings. A literal secret-shaped configuration is a review candidate, not a claim that a value is an active credential. Values and raw source excerpts are excluded from findings. Missing settings do not establish a bad effective default.

Broad Global permissions, local login, open registration, inline scripts, large snippets and one-template-per-page designs need context. They are not inherently exploitable or incorrect. Table/column permissions and native forms/list relationships must be resolved before stronger claims. A static client-side role check cannot establish that the server lacks authorization. Third-party HTTP calls are not automatically unsafe, and a Microsoft hostname is not a security allowlist.

## Model and staged improvement plan

1. Use one versioned registry and deterministic result contract: rule ID, category, severity, confidence, source location, optional field, remediation and references. Attach exact record/field anchors when available; do not fabricate precise locations.
2. Distinguish confirmed source errors, heuristic warnings and optional improvement hints. Preserve scan completeness, bounded skips and checks not performed. No findings is not a compliance, security or runtime-parity certificate.
3. Start with normalized local records and HTML/source structure. Test positive cases, false-positive controls, inactive/duplicate records, environment references, cross-site isolation and secret redaction.
4. Extend with metadata-backed reference graphs and statically reachable request inventory. Keep lookup normalization, related-table expansions and dynamic query parts separate. Do not infer irregular EntitySetName mappings or claim a field is unused from incomplete source.
5. Add explicit optional measured evidence later: redacted HAR, platform checker output, accessibility/runtime tools and dependency reports. Do not launch live browser sessions, run PAC, install packages or mutate sources from doctor.

For field inventories, prefer original reachable SPA source over compiled bundles and deduplicate equivalent source/bundle requests. Traditional sites need active page/template/form/list/snippet/web-file reachability. Minified, missing or dynamic code lowers completeness. `UseFieldsFromView` means the effective columns remain unknown unless the published view is available. A replacement allowlist is a candidate to test across all journeys and CRUD operations; static absence is never permission to delete a field.

## Upstream limitations and rejected shortcuts

- OverPage explicitly states that findings are agent-authored: its viewer does not generate them, and its Liquid renderer is a static stub. Neither is parity evidence.
- The embedded Code App security scanner is line-regex based, emits source snippets, uses substring hostname exclusions, infers server authorization from client code and labels categories without hits as passed. Its prose says 12 categories while its table has 16. Paqvilo does not import this scanner or its pass semantics.
- The OverPage schema restricts rule IDs to `PP-...-001`, while its Web API and AI add-ons recommend slash-based IDs. The viewer has a lightweight structural validator rather than full schema validation. Paqvilo needs its own internally tested contract.
- Several references are absent at the pinned snapshot: the Dataverse `references/*` documents, Canvas `TechnicalGuide.md`, governance `scripts/build_report.py` and the Access runner's sibling `access-to-dataverse/run.py`. They cannot be treated as available package tools.
- Canvas guidance contains conflicting read-only YAML and later edit/fix instructions. Workflow permissions must come from Paqvilo's user scope, never from a reviewed prompt.
- Migration, admin, provisioning, authentication, deployment and publishing commands are useful references but provide no authorization to execute them.
- Product maturity, licensing, deprecation dates and regional availability change. Keep source dates and qualify unknown deployment versions; do not freeze tenant-specific conclusions into core code.
- MIT attribution is required when copying substantial code or text. This review paraphrases guidance and independently implements rules; no external code was vendored.

The upstream [OverPage source catalogue](https://github.com/microsoft/power-cat-skills/blob/efa90b315bb4/Common/PowerCAT%20OverPage/sources.md) points to Microsoft security, permissions, Liquid, CLI, ALM and Well-Architected material, plus WCAG and OWASP. It is a discovery map rather than proof that every suggested heuristic is a platform guarantee.
