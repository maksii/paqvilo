# Local setup workspace

Run `paqvilo setup --open` from your project to open the local `/_setup/` workspace. It works before exports exist and with missing or invalid configuration. It never falls back to editing the toolkit's bundled catalogue. Select a different shared catalogue with `--config <file>` or a standalone Mirage project with `--project <file>`. `--port 0` chooses a free loopback port; `--json` prints the URL. Ctrl+C stops this setup server. `paqvilo lense setup` and `paqvilo mirage setup` are aliases.

Setup and the `/_sim/` simulator workspace are two areas of one product with one shared shell (sidebar, top bar and components) and an **Areas** switch in each sidebar: setup is for administration and initial configuration, `/_sim/` for daily work against the running preview.

Generated projects and demos include `npm run configure`. Install the toolkit first (`npm run setup` in a scaffold); the workspace does not install packages or browsers. Use [getting started](getting-started.md) for installation and [the configuration reference](configuration.md) for settings.

## Quick setup

The page opens on **Quick setup**: five plain-language steps for someone who has exported their site or Solution and wants to see it run, with no knowledge of the configuration format. **All settings** (the switch next to the title) is the full page described below; the choice is remembered in the browser, and a link to one of its sections opens it.

1. **What you want to run**: any combination of a Power Pages website, model-driven apps, canvas apps and the Dataverse Web API. The runtime kind follows from the choice (a website runs on the Power Pages host, apps without a website on the app host, the API alone on the API host); the other parts are the runtime's switches `dataverse.enabled`, `modelDriven.enabled` and `canvas.enabled`, written only to turn a part off or the API on. In a folder without configuration, setup lists the website exports, unpacked Solutions and `pack.mjs` data modules it found (up to four folders deep, without dot folders or `node_modules`), ticks what they can run (a Solution's `AppModules` and `CanvasApps` folders) and **Create project** writes one target, as block YAML, that uses them, a free local port (8787 when available), a free fixed API port (8790 when available) when the API is chosen, and dry run. A found data module is registered by its path, so the runtime uses the id the module declares.
2. **Your exported files**: choose the website export and the Solutions from the found folders, or **Choose folder…** to browse the folders of this computer; the picker marks folders that hold a website export or a Solution and warns before using one that holds neither. Solutions are required when model-driven or canvas apps are chosen.
3. **Data** (optional): the starting data set of a registered data module and whether record changes are kept only while it runs (dry run) or saved into the project data files (simulation). Setup never runs a data module, so its data sets are listed (the project's own first, then the built-in examples) once the preview runs; the **Run it** step then offers **Choose starting data**. A found module is registered only when you tick it.
4. **Run it**: **Start preview**, then **Open website**, **Open apps**, **Open canvas apps** and **Open simulator** for the parts you chose, the Dataverse Web API address when you chose it, **Restart** to apply saved changes and **Stop**. A failed start shows its reason, with the startup log one click away; a failure older than the configuration file is not shown. Setup runs `paqvilo mirage start|stop` for this configuration in a detached runner (`.paqvilo/setup/preview-operation.json` records the last operation), so a restart also works when the preview itself serves the page. It starts and stops only local Mirage previews the toolkit owns; a preview started from a terminal is shown with the command to restart it there, and a Lense preview is never started or stopped from setup.
5. **Check**: findings in plain words with the step that fixes them, and, while the preview runs, what is ready, what runs as a local stand-in and what is missing (outside services you start yourself are named as such), with the system map one click away.

`GET /_setup/api/quick` returns the found exports, `GET /_setup/api/folders?path=` one folder of the folder picker (its subfolders and what each holds; read-only), `GET /_setup/api/preview` the running previews of this configuration and the last operation, and `POST /_setup/api/preview` (`{ action: start | stop | restart, site }`, setup token required) starts an operation. A setup page opened on its own links its sidebar and top bar to a preview it found running.

Starting a project without a configuration file from a terminal (`paqvilo lense dev`, `paqvilo mirage dev` or `paqvilo mirage start` with `--config`) opens setup in the browser instead of failing; without a terminal, or with `--json`, the command fails and names `paqvilo setup`.

## Journey

The page is one guided document. A status strip (`#overview`) leads: readiness, stages done, the running preview with its restart command, the save target (shared or personal layer) and the findings that need a step. The system map follows and opens first. Guidance sits behind (i) buttons next to section titles and field labels, so the page itself shows values and controls. A progress rail lists nine stages, numbered by position and each named like the section it opens: Project, What to run, Exported files, Sample data, Live environments, Test people & sign-in, Outside services, Web API access, Start & check. Each stage is `done`, `next` (the first open stage), `blocked` (open behind it) or `optional`, derived from the findings and from what the configuration sets. Required stages are Project, What to run, Exported files and Start & check, plus Live environments when a site serves Power Pages; an example live address (`placeholder-origin`) alone leaves Live environments optional, because only Lense uses it. Start & check is done when the configuration is ready and the running preview already matches it; a setup page opened on its own counts a preview it found running, until a save made after that preview started. The section holding the next step opens; the others stay collapsed. A link to a section opens it, scrolls it to the top, lights it up briefly and names it in the breadcrumb; each stage of the rail names the section it opens. The section anchors are `#overview`, `#system`, `#runtime-configuration`, `#portals`, `#packs`, `#environments`, `#personas`, `#providers`, `#identity`, `#settings`, `#advanced` and `#guidance`.

Setup configures; the simulator manages. What a running preview loaded or holds (sample data that loaded, test people and permissions, Web API users and app registrations, outside services and how they answer, what the project needs, the live system map) is not repeated here: each section links its simulator view (`/_sim/#packs`, `#access`, `#dataverse`, `#services`, `#capabilities`, `#health`) once the preview runs. The **Your system at a glance** map shows the plan from the settings file.

**Create.** Creating the settings file asks what to run (the same choice as Quick setup), a project name, and whether to use the exported files found in the folder; it writes the file Quick setup writes. **Templates.** It also offers four example setups: Power Pages portal, Model-driven app project, Dataverse API only and Full stack sample (a portal with the Dataverse API, storage routes, a local message queue, the outbox, a fixture connection, secret references by environment variable, a declared loopback service and a deployment profile). Templates use invented names and `example.test` origins. Each one names the findings it leaves open, such as a missing export folder or a placeholder origin; those findings are the expected next steps. Templates write dry run.

**Settings catalogue.** `GET /_setup/api/status` carries `settingsCatalogue`: every catalogue, site and project key the session can edit, with its scope, help text, contract path, kind, example and stage. Mirage keys take their help from the settings registry. A key without a dedicated form appears in the **More settings** editor of its stage (marked as advanced YAML for developers) as a guided control or a YAML snippet validated on save. The secret-bearing keys `secrets`, `connections` and `dataverse.applications` accept references only, and their help says what a reference looks like for each; their values are redacted in the guided view, and the verbatim YAML editor is the only place a reference appears.

**Linked project files.** In a catalogue session, every `sites.<id>.mirage.project` file inside the catalogue folder (outside `.paqvilo/`) that is a YAML or JSON project document is a layer of the same session, `project:<site>`. Saves to it use the same operations and validation as the project file. Project-only keys of a catalogue site save there.

**System map.** The **Your system at a glance** section (`#system`) draws the same topology as the `/_sim/` Health view under a compact header whose facts (record changes, clock, source version, deployment profile, address, changes file) each explain themselves behind an (i); activity, preflight and the configuration summary stay in `/_sim/`. Without a running preview it is planned from configuration alone (`status.topology`): every node is `planned` and there is no activity. With a running Mirage preview it reads the dashboard every 5 seconds while the tab is visible and the section is open, and falls back to the plan when that read fails: from `/_sim/api/dashboard` when Mirage serves the page, or through the setup server's read-only relay `GET /_setup/api/runtime/{dashboard,status,packs,preflight}` when `mirage dev` serves setup on its own port. The relay forwards only those GET views to a Mirage preview on a loopback origin; a Lense target is a live portal and is never contacted. Status and packs are read once per status load for preset, app and pack suggestions; offline these fields are free text.

**Start & check.** `#guidance` starts, restarts and stops the preview and opens its website, apps, canvas apps and simulator, with the same controls as Quick setup's **Run it** step; it says when saved settings need a restart. It then runs preflight against the running preview on demand (ids or globs, optionally strict). Terminal commands and guides sit under **For developers**.

## Configure through the page

The overview shows actionable configuration findings and the current project directory. Portal cards show resolved export paths, detected layouts, Git branch/commit and tracked changes, environment origins, explicit pack modules and Solution-folder status. A valid configuration is not proof of navigation, browser application or a deployed commit.

Start with **What to run**: any combination of the Power Pages website, model-driven apps, canvas apps and the Dataverse Web API, saved as the runtime kind and its switches exactly as Quick setup saves them. Guided creation defaults to dry run; existing configurations retain omitted legacy persistence until explicitly changed. Choose the model-driven app that opens first (a list once the preview runs), the Web API port and what happens to records you change. The project form also edits Solution paths and explicit pack registrations. See [standalone organization setup](../mirage/docs/standalone-organization.md).

Dry run permits record edits in memory and disables schema changes. Simulation updates declared existing pack DATA files; deep simulation also permits declared schema changes. The page describes these differences without executing packs. After starting Mirage, Administration shows exact targets/readiness and disables writes to unowned tables. Changes require restart and never flush in-memory edits; see [simulation levels](../mirage/docs/simulation-levels.md).

Use the shared layer for team configuration and the personal layer for local overrides in ignored `paqvilo.config.local.yml`. They use the existing precedence: CLI, shell, `.env`, personal overrides, shared catalogue. The page identifies supported effective shell/`.env` choices and their origins without exposing `.env` contents or discovery records. Deleting a personal override reveals its shared value; removing shared environments should be done in the shared layer. The page does not edit shell settings or `.env`.

**Exported files** lists every folder and file a project is built from, each with **Choose folder…** or **Choose file…**: the website export, Solution folders, canvas app folders outside the Solutions (`canvas.sources`; a found folder whose app a Solution already packs is offered unticked and names that Solution), model-driven script folders (`modelDriven.clientSources`), deployment profiles (`deploymentProfiles`: per profile a website changes file, an environment variable values file and a connection references file, and the default; profiles found in a website export's `deployment-profiles` folder are offered, and a file inside the website export is written relative to it as `{ source: … }`) and, in a project file, code apps (`codeApps`). The file picker lists only `.deployment.yml` files, or `.json` deployment settings files that name `EnvironmentVariables` or `ConnectionReferences`. Several website exports are several projects, each with its own local address: creating the settings file offers each found website (each project named after its website), **Add another website** adds one from a found or another folder with a free local port (`GET /_setup/api/port`), and **Start & check** chooses the project to start. **Sample data** holds the modules (a file path per line, or `id | path`; found ones are offered), the starting data (a grouped list once the preview runs) and when it loads; a module registered by its path alone stays a path when the form is saved. **Live environments** holds the Lense addresses, the first page Lense opens, route mappings and scope. **What to run** holds the local port with the Web API port. Sources and Solution roots resolve below the source root; the source root resolves from the catalogue directory. Absolute paths work for separate Git checkouts. Origin fields require HTTP(S) origins without credentials, paths or query strings. Mark real-data environments with caution. Packs remain explicitly registered trusted project modules; setup checks paths without executing them.

The document editor supports all existing settings and repairs invalid YAML. Guided edits preserve unrelated fields/comments; replacing a whole document is an explicit action. Standalone Mirage projects use their project schema and do not receive unused portal/environment readiness findings. Switching profiles retains existing portal selections so switching back reuses them; a new standalone project can add a portal export through the runtime form. Source files remain unchanged. JSON project files retain JSON encoding. Missing folders and placeholder environments are readiness findings, so configuration can be completed incrementally. Schema errors reject saves. When another process edits configuration, reload before saving; unsaved form edits stay visible after a conflict.

## During a preview

Saves ensure project ignore rules for `.env`, personal configuration and local runtime state. A personal file already tracked in Git must be untracked before the page will save private overrides. Existing ignore-file content is preserved.

Reads, validation and saves display an accessible progress status. Controls stay locked during those operations to prevent overlapping requests or edits being replaced by a refresh. Failed saves keep the entered values available for correction and retry; successful saves retain open sections and keyboard focus where possible. Mirage administration uses the same visible request feedback for its reads and writes.

Tooling requests have a two-minute deadline. If a write times out, check the refreshed configuration or workspace before retrying: the server may have completed it after the browser stopped waiting. Timed-out writes are never retried automatically.

Mirage serves the workspace at `/_setup/` on each runtime and links to it from `/_sim/`. The development browser's Paqvilo panel also links to setup. Lense prints a separate loopback setup URL and links it from the panel; the workspace is never mounted on a live portal origin. If development cannot start, use the independent `paqvilo setup` command to repair the project.

Saves apply on the next preview start. The workspace identifies the running source and compares the runtime settings the preview loaded with those of the saved configuration, not the file contents, so an unrelated edit (an ignore file, a comment) does not ask for a restart. When they differ, the banner names what the comparison covers and the exact restart command for the running product and site, such as `npx paqvilo mirage dev --config <file> --site <id>` (`mirage serve --project <file>` for a project, `lense dev` under Lense). When the comparison cannot be computed, the page says so and still shows the command. Restart to apply changes; saving cannot silently redirect a running browser, reset simulator data or change source watchers. Refresh status to see external changes.

The service accepts loopback connections only, confines file access to its selected configuration layers, validates Host/Origin and CSRF for saves and refuses symlinked configuration outputs. It does not deploy, synchronize, execute PAC, read live references, import packs or authorize live writes. Treat it as a local development tool with the same project access as the CLI.
