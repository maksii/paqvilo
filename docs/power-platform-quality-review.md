## Power Pages: deterministic checks and cautions

[Performance catalog](https://github.com/microsoft/power-platform-skills/blob/2eb182a8b7a2/plugins/power-pages/skills/analyze-performance/references/performance-reference.md) documents stable tags, severities, source locations, fixes, exclusions, thresholds and Learn references. The [implementation](https://github.com/microsoft/power-platform-skills/blob/2eb182a8b7a2/plugins/power-pages/skills/analyze-performance/scripts/analyze-performance.js) is offline and deterministic. Its separate AI mitigation pass preserves original rule fields. Paqvilo should own a small independent module rather than install the plugin or silently run its agent fallback.

High-value initial checks:

- Explicit FetchXML all-attributes: warn about projection and data volume. Missing columns/paging and large result caps are advisory; aggregates require exemptions. FetchXML in a Liquid loop is a possible N+1, not proof of latency. Query hints may be intentional measured optimizations.
- Web API query projection and paging: review wildcard/missing select, counts and related expansions. `Prefer: odata.maxpagesize` with `@odata.nextLink` is valid cursor paging; `$top` is a result cap, not the only valid paging method. Dynamic URL builders cannot be comprehensively understood by a string scan.
- Blocking browser patterns: parsed external head scripts without defer/async/module, synchronous XHR, synchronous jQuery AJAX, document.write and runtime CSS imports. CSS preprocessing imports are different. A source hint cannot establish measured paint timings.
- Explicit disabled header/footer output caching and tracking settings: advisory with a reminder that output caching also requires substitution tags in Header/Footer/Languages-Dropdown templates. Do not auto-enable caching or infer old/new-site defaults from an absent setting.
- Asset and record volume thresholds are review heuristics. Upstream defaults of 100 rows, 20 columns, 500 web files, 100 roles and 1 MiB are not platform support limits.

[Site settings validator](https://github.com/microsoft/power-platform-skills/blob/2eb182a8b7a2/plugins/power-pages/scripts/lib/site-settings-validator.js), [permission validator](https://github.com/microsoft/power-platform-skills/blob/2eb182a8b7a2/plugins/power-pages/scripts/lib/table-permissions-validator.js) and [web role validator](https://github.com/microsoft/power-platform-skills/blob/2eb182a8b7a2/plugins/power-pages/scripts/lib/web-roles-validator.js) provide schema and relationship consistency ideas. Their strict field allowlists, hand-written YAML subset and version-specific UUID regex must not become universal export validity rules. Paqvilo must preserve aggregate/per-record and standard/enhanced forms, record identity, languages and unknown sibling fields. Missing relationships can be detected locally; relationship existence requires Solution metadata or separately authorized live evidence. Missing linked records can reflect partial exports.

[Web API field contract](https://github.com/microsoft/power-platform-skills/blob/2eb182a8b7a2/plugins/power-pages/references/webapi-field-allowlist.md): normal properties use exact LogicalName; lookup reads use `_LogicalName_value`; relationship writes use the exact navigation property before `@odata.bind`. Do not lowercase or substitute SchemaName. API paths use EntitySetName; settings use LogicalName.

Current official guidance cross-check, retrieved 2026-11-05: [Web API overview](https://learn.microsoft.com/en-us/power-pages/configure/web-api-overview), [wildcard migration](https://learn.microsoft.com/en-us/troubleshoot/power-platform/power-pages/migrate-web-api-wildcard), [deprecations](https://learn.microsoft.com/power-pages/important-changes-deprecations). Wildcard fields support was removed September 14, 2026. Temporary exemptions exist, so source analysis identifies incompatibility rather than asserting a live outage. A missing explicit fields list is allowed when `Webapi/<table>/UseFieldsFromView=True`; that feature requires site 9.8.8.x and an eligible system view. A local export cannot establish view contents or site runtime version without evidence. Both settings combine their columns.

[Authorization reference](https://github.com/microsoft/power-platform-skills/blob/2eb182a8b7a2/plugins/power-pages/skills/setup-auth/references/authorization-reference.md) emphasizes that client-side role/UI visibility does not enforce server authorization. Anonymous table access is a review finding because intentional public catalogs exist. Inner-error disclosure, literal secrets and permissive configuration deserve warnings; never print secret values or customer source excerpts. Source-only coverage does not prove effective authentication, table/column permissions, CSP, firewall or identity-provider behavior.

## ALM, evidence and workflow lessons

[ALM workflow](https://github.com/microsoft/power-platform-skills/blob/2eb182a8b7a2/plugins/power-pages/skills/plan-alm/SKILL.md) verifies environment alignment before discovery and separates actual source facts, estimated sizes, strategy defaults and user decisions. [Threshold configuration](https://github.com/microsoft/power-platform-skills/blob/2eb182a8b7a2/plugins/power-pages/scripts/lib/alm-thresholds.js) uses project-overridable split recommendations; its 75 MiB/4000 component defaults are not platform caps. Solution completeness, dependencies, managed/unmanaged strategy, connection references, environment-variable definitions/values and Key Vault secrets are future source/Solution review topics. Export operations may bump remote versions; do not label them read-only merely because their name is export.

[Setting classification](https://github.com/microsoft/power-platform-skills/blob/2eb182a8b7a2/plugins/power-pages/scripts/lib/classify-site-settings.js) distinguishes secret-like names from ordinary client IDs. Do not flag client IDs as leaked secrets. Environment-backed values require resolution evidence; an absent literal is not an absent deployed setting.

[Verification evidence](https://github.com/microsoft/power-platform-skills/blob/2eb182a8b7a2/plugins/power-pages/scripts/lib/verification-evidence.js) hashes exact source, dependency and build inputs; stale or partial reports do not authorize whole-site success. [Test workflow](https://github.com/microsoft/power-platform-skills/blob/2eb182a8b7a2/plugins/power-pages/skills/test-site/SKILL.md) records passed/failed/skipped and current-run evidence rather than stale prose counts. Browser authorization gates, anonymous expected denial, authenticated coverage and source checks must stay distinguishable.

[Security-review orchestration](https://github.com/microsoft/power-platform-skills/blob/2eb182a8b7a2/plugins/power-pages/skills/security-review/SKILL.md) separates local code/config review from live scans. It preserves scanner severity and does not invent severity for plain inventory. Paqvilo-owned rules may define documented severity, but imported third-party reports must retain provenance and tool status. Skipped/unavailable/failed analysis must never become zero findings or a successful certification.

Localization/RTL checks need declared locale context: logical CSS properties, explicit-direction exceptions and rendered component-state checks cannot be validated by simply finding left/right strings. [Native authoring guidance](https://github.com/microsoft/power-platform-skills/blob/2eb182a8b7a2/plugins/power-pages/AGENTS.md) explicitly treats local structural results and plan HTML as provisional, preserves serialization/locale/record identity and separates external image availability/privacy/CSP/licensing from local edits. These distinctions align with Paqvilo's source editing and evidence boundaries.

## Model for follow-up work

Keep deterministic rules and stable IDs independent from CLI presentation. Every finding should name severity, category, confidence, source-relative file/field and precise versus approximate location, documentation and safe remediation. Track what was analyzed, skipped, truncated or unsupported. Avoid customer text in messages and excerpts; diagnostics should be useful with field/location only. Do not execute source, Liquid, project npm scripts or external packs while inspecting it. Apply bounded input/output limits and do not follow symlinks out of the selected source. Treat warnings as opportunities for review and errors as known local contract/incompatibility failures. Own-rule tests are contract/tooling/security tests, not native parity.

Deferred work needs explicit adapters and tests: full FetchXML/JavaScript parsing, Web API request-to-field data flow, Solution relationship/column metadata, PCF manifest/host compatibility, multilingual associations, SARIF/external scanner import, suppressions with reasons, exact-input baseline comparison and separately authorized runtime accessibility/security testing. Do not imply the first offline rule set covers those concerns.
